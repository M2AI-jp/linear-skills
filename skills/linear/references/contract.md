# Linear共通運用契約

利用側の既存入口から、対象Projectまたは新規作成の意図、原要求・正本、今回の責任範囲と既存の許可を受け取る。既知の対象や許可は再質問せず、特定に必要な許可済み調査を進める。不明な業務判断は確認し、その判断に依存する変更を止める。対象と正本に矛盾があれば原因を照合し、未採用の判断を補完しない。

本書が状態・行動・受入の共通規則を一つだけ持つ。現在の採否・担当・依存・未達は対象Linear、実装版は利用側のGit、業務の実結果は各成果物を正本とする。呼出側が本書を参照し、本書は特定Projectや個人環境へ依存しない。

内容: 文脈と正本／Linearの単位と状態・遷移／Codexの行動／スキルとHook／コードと外部操作／実行サイクルと完成条件。

## 文脈と正本

| 対象 | 扱い |
|---|---|
| 要求・要求変更 | ユーザー原文と採用された判断が根拠。AIの設計案と区別する。 |
| 全体範囲・現在地・担当・依存・未達 | Linear。確定した未着手要求を、今回やらないという理由で消さない。 |
| コード・テスト・設定・スキル・Hook | Git。実行する版と経路を特定し、旧案を現行入口やフォルダへ残さない。 |
| GWS・GUI・外部サービス・現場 | それぞれの成果物と実状態。予定、実施報告、保存応答、実際の反映を区別する。観測できない結果を補完しない。 |
| 判断理由・インシデントの証拠 | 原文・Issue履歴・実行記録・Git／CIへの参照。正本を複製する独自JSON台帳やreceiptは作らない。 |
| 会話・要約・過去の報告 | 調査の手掛かり。現行指示として復活させない。ファイルの削除で会話内の旧文脈まで消えたとは主張しない。 |

計画の受入では、原要求ごとに必要な仕事・受入・依存・更新先があり、根拠のない機能や手続きを加えていないことを確認する。計画の一致と実装・運用の有効性の実証を分ける。

Projectの全体像を確認してから、今回の責任モジュールと必要な依存先へ絞る。訂正は現在判断を所有するIssue・正本から行い、その判断を入力にするIssue・Milestone・Project・入口の旧指示も置換して読み戻す。他Issueの状態・次作業の写しは所有Issueへの参照に置き換える。過去証拠は対象版・範囲と履歴への参照で保持し、現行指示と混在させない。ユーザー原文、有効な未着手要求、無関係な変更は保持する。

対象Projectを固定し、他のProjectを参照して文脈を補わない。新規作成は明示された意図・対象資料から始め、必要なチーム・状態の実在を確認する。既存Projectをひな型として探索しない。明示的なLinear利用または導入済み対象の入口から起動し、無関係なリポジトリでは自動起動しない。対象未特定の操作は止めるが、対象を特定するための許可済み調査は進める。

共通スキルに特定ProjectのID・個人のパス・特定業務の仕様を埋め込まず、利用側の対象と正本を入口から渡す。検証用Projectも、その試行で指定された対象だけを扱う独立した文脈・入口で実行し、別のProjectの現在指示と混在させない。

LinearではProject本文を全体像と正本の入口、Documents／リンクを詳細仕様や外部成果物の参照、Issueを仕事・担当・依存・受入、Updates／コメントを判断理由と履歴に使う。現行判断は本文と状態に反映する。日時・場所・人の引継ぎがある仕事は、それらと実結果の確認者をIssueに明示し、必要な期日・Milestone日程・Cycles・Viewsを実際の運用に合わせて使う。GWSの予定や資料を無条件に複製しない。リポジトリを持たない業務にもGitやローカルSSOT.mdを必須にしない。

## Linearの単位と状態

Projectは業務全体の成果と完成条件を持つ。Milestoneは疎結合なモジュールが使える到達点であり、責務・入力・出力・依存方向・処理順・受入を持つ。各Milestoneに「何を変更すると、どの接続先の何を更新・再評価するか」を明示する。Issueは主体・対象・前提・変更責任・受入・更新先が明確な仕事。調査、判断、コード、GUI、人の作業、評価を含む。

状態の意味と採否・受入を判断する原則は共通契約に置き、現在の採否判断はLinearに保持する。Hookは共通契約の機械検査、Refreshは計画の構築・再整理、PMは実行・訂正・引継ぎ、Git／GitHub運用は版と統合、業務受入は接続した実成果を担う。共通契約への参照で接続し、各実装へ異なる規則を複製しない。これらの具体的な作業配置はLinearに保持する。

着手に先行成果が必須ならBlocked byで表す。共同設計・変更通知・受入時だけの接続はRelatedと本文で区別し、見かけの依存で並列作業を止めない。独立したモジュールは入力・出力の契約と必要な実行制御が成立してから並列に進める。契約変更時は影響先の本文・状態・依存・試験を訂正し、影響しない仕事を一律にやり直さない。

既知で採用済みの全範囲を、未着手分も含めて責務・ファイル・外部副作用・検証対象が混ざらない仕事へ分解する。Issue数を上限で抑えない。仕様が未確定なら、その仕様を決める仕事と後続の既知範囲を保持し、架空のファイルや仕様は確定しない。各Issueは先行する仕事と受け渡す成果を示し、先行がなければ起点となる原要求を示す。実装前の設計と実装後の試験は着手時期が異なるので、同じBlocked byで一括して止めない。

状態は保存された判断であり、現在の操作を無条件に許すものではない。新しい証拠と現在の依存を照合してから利用する。

| Issue状態 | 意味 |
|---|---|
| Triage相当 | 報告・案を受領したが扱いは未判断。確定仕様として実装しない。状態がなければ本文で採否未定を明示する。 |
| Backlog | 必要な仕事だが着手順・準備が未成立。候補と採用済み要求は本文の根拠で区別し、状態名だけで採用を推定しない。 |
| Todo | 主体・対象・受入・着手前提が明確な未着手作業。調査は調べる対象と完了条件が明確なら着手できる。 |
| In Progress | 担当が実行中、受入未完了。作成しただけの成果を後続の確定前提にしない。 |
| In Review | 評価対象の成果があり受入確認待ち・確認中。版・環境が変われば影響する評価を更新する。 |
| Done | そのIssueが約束した成果を現在の要求に対して確認した。調査完了は採用を意味しない。部品の完了を全体完成へ拡大しない。 |
| Canceled | 実施しない判断が成立。理由と必要なら代替先を示す。失敗・待機・未確認を隠さない。 |
| Duplicate | 正本Issueへ集約。要求の行方を失わず、重複整理を成果の完成に数えない。 |

Blockedは段階と別の依存。Blocks／Blocked byに、誰の何がそろえば再開できるかを結び付ける。Relatedは先行必須を意味しない。先行Issueを再開した際は必要な依存も確認し直す。

Milestoneは未着手 → 作成・接続・評価中 → モジュール受入成立と解釈する。進捗表示は所属Issueから計算されるため受入の代用にしない。接続先が出力を利用できることを所属Issueの受入へ含め、独立した仕事になる場合は受入Issueを置く。全IssueがDoneでも利用者経路が成立しないなら計画の欠落を訂正する。新証拠で根拠が崩れたら該当Issueを再開する。

| Project状態 | 意味 |
|---|---|
| Backlog | 取り組みの候補。採否や時期は未確定。 |
| Planned | 実施を採用し、目的・範囲・完成条件・責任者・最初の進め方が明確。実行前。 |
| In Progress | 目的達成へ実行中。全体受入は未成立。 |
| Completed | 今回必須の採用範囲の利用者体験・非機能要件・外部結果が成立。保留は下記の判断に従って残す。進捗率や全IssueのDoneから自動推定しない。 |
| Canceled | このProjectの実施を取りやめた。目的達成や一時保留を意味しない。 |

根拠が否定された仕事は、実行待ちならTodo、修正中ならIn Progress、再評価だけならIn Reviewへ戻す。影響する依存先・Milestone・Projectの完了も訂正する。無関係な完了は戻さない。対象・採否が不明な変更は確認する。

### 遷移の主体・根拠・制約

PM役のCodexが原要求・採用判断と実結果を照合して状態を更新する。実行担当は成果、テストレビュー担当は試験の妥当性、QA担当は実装・外部結果を返す。ユーザーにしか決められない業務判断はユーザーが決める。通常の実装・評価判断を毎回ユーザーへ戻さない。表は運用仕様であり、現Hookがすべて実装済みという意味ではない。

| 遷移・操作 | 更新する主体と必要な根拠 | Hook／実行制御と不成立時の扱い |
|---|---|---|
| 受領 → Backlog／Todo | PMが原要求・採否・担当・対象・受入・先行成果を確認。未採用案は候補と明記。 | 対象Projectと実在状態を照合。未確定の採否を推定しない。調査自体を仕事にする。 |
| Todo → In Progress | 実行担当が前提を確認し、PMが担当する版・対象・先行成果の成立を確認。 | 別Project、取得失敗、未成立の必須依存からの着手を拒否。読取と前提の訂正は許す。 |
| In Progress → In Review | 実行担当が評価可能な成果と実行結果を渡す。コードはモジュールPRの候補版、非コードは対象の反映結果を特定。 | PR作成や保存応答を受入済みとしない。対象不明・部分反映は修正側へ戻す。 |
| In Review → In Progress／Todo | テストレビュー・QA・反証で不合格。PMが原因と影響先を特定。 | 実装修正中はIn Progress、修正着手待ちはTodo。再試験する根拠だけを更新し、古い合格を流用しない。 |
| In Review → Done | PMがその仕事の受入を実データから確認。コード・テストはモジュールのlint・実試験・独立したテストレビュー／QAを通す。Git統合の仕事はE2Eを通した版のmain反映まで確認。人・GUIの仕事はその結果の観測まで確認。 | 未完了依存・古い版・失敗／未実行の必要試験を検出したら拒否。チェック名・リンク・自己申告だけで許可しない。コード変更の受入とmain統合を別Issueで扱う場合、Doneをmain反映と誤認しないよう採用先を本文に明示する。 |
| Done → 未完了 | PMが新証拠で失効した要求・成果・テストを特定。本人の過去の完了報告も対象。 | 訂正を許し、修正待ち／修正中／再評価に応じてTodo／In Progress／In Reviewへ戻す。依存先・全体受入・現在本文を訂正して読み戻す。 |
| 任意 → Canceled／Duplicate | PMが中止の採用判断または集約先と要求の移行を確認。 | 理由や集約先がない未達隠しを認めない。先行仕事の中止を後続の受入成立にしない。 |
| Project → Completed／再開 | PMが全体範囲と接続した利用者体験・非機能・外部結果を確認。反証があればIn Progressへ戻す。 | Issue進捗の集計から自動承認しない。対象・先行成果の機械検査と業務の意味の評価を分ける。 |

コード変更、PR作成・レビュー・統合、外部設定は成果の種類が異なる。Issue本文で採用先と完了の範囲を決め、未mergeのPRをmainへ反映済みと報告しない。実装を受け取ってから始める統合Issueを、実装Issueの完了条件へ循環させない。受入条件の変更は元の要求から評価し、試験を通すために弱めない。

Milestoneには独立した任意の状態欄を捏造しない。所属Issueの状態から示す進捗と、本文のモジュール受入を区別する。Blocksが解消されRelatedへ変わる場合があるため、先行の再開時には元の必須関係も確認する。取得失敗・外部からの状態変更・自動クローズを新たな合格証拠にしない。

## 今回必須と保留の判断

PM役のCodexは問題を発見したら、今回の完成に必須か、放置した場合の影響、修正と検証に必要な時間・token・外部費用を判断する。必須は修正し、非必須は保留して元の仕事を進める。普通の未完了仕事は既定で必須。費用が高いという理由だけでユーザーの必須条件を外さず、採否が未確定ならその判断に依存する操作だけを確認待ちにする。

保留はLinear標準のBacklog（state.type=backlog）と厳密名DeferredのIssueラベルを併用し、本文に保留理由・影響・再開条件を短く保持する。ラベルは機械識別であり、意味の採否証明ではない。保留をCanceled／Doneに偽装せず、全体の将来作業に残す。掘り起こすのは新証拠または再開条件成立時だけ。必須仕事がその未完了成果に依存するなら、保留を理由に必須仕事やProjectを完成にしない。

現在の採否・仕様・テスト・Doneが誤っている場合は直ちに訂正する。製品欠陥自体の修正は上の判断で保留できる。判断と正本の訂正、製品実装の修正を混同しない。計画生成・整理は原要求に必要な範囲で完結し、例に挙がった製品全体の完成をスキル試験へ追加しない。

独立評価・再試験・新しいLLMの起動は変更リスクと必要な文脈分離に比例させる。既存合格を新しい根拠なく繰り返さず、小さい更新ごとに新担当を立てない。必要な独立評価は評価待ちとして残し、自己点検で代用しない。

Project Completedの機械検査では、非終端IssueのうちBacklog＋Deferredだけを今回完了の検査から除外し、その他の未完了を拒否する。非保留かつ非Canceled／DuplicateのIssueはDoneも含め、未完了の先行依存があれば拒否する。ラベル・依存の取得不足や本文の自己申告で通さず、受入範囲変更とCompletedを同時に更新しない。機械検査通過後もPMの意味と外部結果の評価は残る。

## インシデントを踏まえたCodexの行動契約

運用中に発生した問題はインシデントとして扱う。観測事実と原因の推定を分け、同じ原因の発生を集約しても各証拠は保持する。過去のAI回答を正解にせず、通常入力から再発を試験する。

| インシデント | Codexに期待する挙動・再発試験 | 禁止する挙動 |
|---|---|---|
| AI追加の管理方式が要求化した | 原要求・採用判断・設計案を区別し、変更の根拠を照合する。 | AI案・Hook生成文を要求や採用済み仕様へ昇格させる。 |
| 旧SSoT・旧Doneが次回の前提になった | 現行Projectと反証を読み、本文・状態・影響する依存を訂正して再開する。 | 古い会話・報告だけで着手する。訂正を追記して矛盾する旧指示を残す。 |
| 限定試験を広い完成条件へ拡張した | 試験の対象・版・実行経路・外部結果を対応させ、未実行・省略・未確認は未達とする。 | 統合拒否だけで修正・再試験・統合を合格にする。部品合格を全体完成へ拡張する。 |
| 確認欄を足しても業務が成立しなかった | 受付担当者が申込情報を使えない等の入力から、計画・受入自体の欠落を訂正する。 | 実装に合わせて期待結果を作り、記録欄の充足を実成果の代わりにする。 |
| 訂正が正本・状態へそろわなかった | 部分反映を切り分け、反映済み操作を重複させず残りを訂正して読み戻す。 | 保存応答・実施報告だけで実際の反映を認定する。未確認の人・GUIの結果を補完する。 |
| 注意文追加・監督確認・停止が連鎖した | 失敗案を戻し、原因の仮説を絞る。正常な再開も試験する。読取依頼は回答で完結する。 | 同じ失敗に同じ注意や手続きを追加する。承認済みの作業を再確認し続ける。 |
| 配置・発火・自己報告を有効性と混同した | 実際の起動・操作経路で、不正操作の拒否と訂正後の正常操作を確認する。 | Hook設定・発火・自己申告を強制力や意味の正しさの証明にする。 |

実行主体のCodexはこの契約に従い、委任時も主語・対象・依存・更新先を渡す。ユーザーによる採否判断、人による現地作業、サービスの実結果をCodex自身の完了と取り違えない。各挙動について、Hookが拒否できる範囲と意味・実成果の評価に残る範囲を分けて確認する。

## スキル群とHook

| 責任 | 入力 → 出力 | 依存方向・変更の影響先 |
|---|---|---|
| Linear入口 | 明示利用または導入済み入口の対象・正本・意図 → 呼出先と受渡し | 共通契約を参照し、必要なRefresh／PMを選ぶ。対象や呼出条件の変更は両系統と導入経路を再評価する。 |
| linear-refresh | 原要求・指定された既存実態・採用判断 → 全体範囲、現在の計画、正本、未確定判断とその担当 | 共通契約に従い計画を構築・再整理する。出力をPMへ渡し、変更した計画・依存・受入はPMと業務評価へ返す。 |
| linear-pm | 対象の現在計画・原要求・今回の責任・実結果 → 成果、採否と状態の訂正、残作業と引継ぎ | 共通契約を参照する。計画の構築・再整理が必要ならRefreshへ対象と根拠を返し、その結果から再開する。 |
| Hook | 対象入口・現行状態・操作引数・結果 → 実行可否、現在文脈、読戻し | 共通契約の機械検査を担う。判定・取得・起動経路の変更は利用側の拒否と正常系へ返す。 |

対象・正本・原要求・既存の許可を呼出間で維持し、全体の未着手要求と今回読む範囲を別に渡す。RefreshとPMの共同設計や相互訂正はRelatedで表し、利用に必須の先行成果だけをBlocked byにする。共通契約の変更は両系統・Hook・Git運用・受入の影響部分へ返す。呼出先が未導入なら、その接続不足を明示し、実行済みと扱わない。

Refreshは意図または既存リポジトリ・資料・外部実態から計画を構築・訂正する。PMはProjectから開始・再開し、今回の文脈を回収して成果・評価・訂正・引継ぎまで進める。複数スキルを利用する入口は、どのスキルをどの順で呼ぶかだけを簡潔に示す。共通の状態定義は本書を参照し、別々の規則へ複製しない。

工程を、開始・文脈回収、計画と採否、変更、lint・試験、テストの定性レビュー／QA、Git操作、正本の訂正と引継ぎの呼出単位として組み込む。コードを変更するときにlint・コード試験・Git操作を適用し、非コード業務では実際の成果物・権限・引継ぎを評価する。不要な工程を実行したふりにしない。Issueまたは必要なIssue集合の中で小さなサイクルを完結し、清掃を最後の工程だけに延期しない。参照・呼出順と必要な入出力を入口から辿れるようにし、毎回すべての注意事項を読み込ませない。工程ごとの新しいサービスや台帳は作らない。

Hookは実行経路への接続と、機械的に確認できる不正操作の拒否を担う。本文・確認済みフラグ・リンクの存在だけで意味の正しさを認定しない。意味の照合とブラックボックス評価はスキルと評価担当の責任であり、Hookの合格で代用しない。

Hookを先行させる目的は、後工程のCodexの操作を実際に制約すること。要求・状態契約を整え、通常の起動経路で不正操作の拒否と必要な正常操作・訂正の通過を確かめてから、後続のスキル実装・業務運用へ進む。Hook未稼働の調査、契約の訂正、Hook自身の実装・試験はこの前提を整える仕事として行える。未稼働を理由に止まり続けたり、黙って制約なしの後工程へ進んだりしない。

| イベント | 責任 |
|---|---|
| SessionStart（開始・再開・圧縮後） | 現行Projectを取得して入口へ接続。要求・担当・依存を回収し、旧報告だけで変更を再開しない。 |
| UserPromptSubmit | ユーザーの追加・訂正を現在の要求・計画へ照合。Hook生成文をユーザーの業務要求として保存しない。 |
| PreToolUse | 対象と現在の前提を検査し、対応する不正変更を同期的に拒否。読取・原因調査・必要な訂正は一括禁止しない。 |
| PostToolUse | 変更先を読み戻す。成功応答だけで完了せず、部分反映を明示。無条件の書込再試行をしない。 |
| SubagentStart／Stop | 必要時だけ責任範囲・原要求・依存・更新先を渡す。子の自己報告を親が無条件に採用しない。 |
| Stop | 今回の成果と報告を照合。同じ指摘の無限再開を防ぎ、読取だけの依頼で記録を増やさず元の質問へ回答する。 |

順序が必要な検査は一つの同期処理で行う。出力を短くし、通常の読取へ長い指示を繰り返し注入しない。取得失敗は成功にせず、依存する変更を止める。再取得・訂正・復帰は可能にする。

Hookだけでは意味の真偽、対象外経路、無効化・未信頼の状態を完全に制御できない。PostToolUseは副作用を取り消さず、Stopのblockは続行指示。MCP Hookの接続エラーやファイルの存在を強制力と数えない。CLI、Desktop、実際のAPI／MCP／必要なGUI経路を区別して試験する。

拒否だけでなく、正しい受入を許可して正常に再開する経路も最終受入の対象である。自己申告の許可フラグだけで検査を通過させない。実装範囲・暫定の拒否制限・未実証の経路は現行Projectに明示し、恒久的な運用要求へ昇格させない。

## コード・構造・外部操作

常にSOLIDを守り、責任・入出力・接続契約・依存方向でモジュールとフォルダを分ける。コードIssueは1ファイル単位。PR・lint・テストとその妥当性評価は疎結合なモジュール単位。非コード作業は主体と結果を確認できる責任単位。

実装前に、そのリポジトリの技術スタック・フレームワーク・依存・リンター・試験方法・PRの区切り・採用先を調べて選定し、正本へ固定する。既存の道具を使い、不要なフレームワークを追加しない。仕様や成功基準を決める仕事もLinearで先行して管理する。ルートAGENTS.mdは正本と固定した開発方針へ接続し、各責任フォルダのAGENTS.mdはその役割・境界・必要な依存だけを短く示す。テストも責任モジュールへ分ける。構造変更で影響する入口と検証を同時に訂正する。

独立した採否判断、並行作業、試行はブランチで分け、復帰点を保持し責任ごとにコミットする。失敗案は差分で撤回・修正し、その上へ対症的な仕組みを積まない。ユーザーの既存変更を巻き込まない。

Main候補はモジュールの依存・lint・テスト・テスト妥当性の確認と、接続した利用者経路のE2Eを通す。GitHub側の保護と必須チェックを併用し、試験対象の版と実結果を確認。skip・neutral・マージ・チェック名の存在だけでE2E成功としない。受入条件や検査を弱める変更は通常の実装と区別して評価する。

Linearは利用可能な通常MCPを先に使う。必要な操作・取得項目が不足する場合だけ、その対象と不足を特定し、既存接続の公式API、必要ならGUIへ切り替える。MCPで足りる操作のためにシェルGraphQLや認証取得を始めない。Hookの拒否は前提の訂正へ返し、別経路で迂回しない。人やサービスの結果を推測で確定しない。操作前に対象を特定し、後に実データを読み戻す。複数の保存先を原子的に更新できると仮定しない。

## 実行サイクルと完成条件

Projectと原要求を確認 → 主体・依存・受入・期待結果・正本・更新先を特定 → 矛盾する現行文脈を除去・置換して読み戻す → 今回必須と保留を判断 → 必須の変更とリスクに応じた評価を実行 → 実結果に合わせて正本と状態を訂正 → 次の担当が再開できることを確認する。

ブラックボックス評価はユーザー要求から期待結果を定め、通常入口から実行して外部結果を観測する。内部出力から正解を逆算しない。独立評価が必要なら文脈を分離し、実装者の答えを注入しない。評価者の結論も証拠へ照合する。

実装、テストの定性レビュー、実装・業務結果のQA、PMの採否判断を責任として区別する。必要な権限と入力を担当へまとめて渡し、同じ確認や短い監督往復を繰り返さない。文脈分離が必要な評価では利用側で採用した評価環境を使い、独立評価を実行できなければ自分の再読を独立評価済みとしない。未知の案件、中断・再開・圧縮後の訂正の必要な評価範囲を選び、特定業務の例への適合だけで汎用性を認定しない。

| 評価対象 | 完成の根拠 |
|---|---|
| 運用契約とスキル・Hook・Git／GitHub制御 | 通常の依頼から構築・実行・拒否・訂正・正常な再開・統合・引継ぎが成立する。Codexの期待する挙動と禁止する挙動を実際の経路で確認できる。 |
| 生成・更新したLinearとSSoT | 原要求・全体範囲・現在判断・担当・依存・受入・正本が実態と一致し、計画自体の誤りも訂正できる。 |
| 管理する業務の成果 | コード・GUI・サービス・人の作業を接続した利用者体験と非機能要件が実際に成立する。上の二つで代用しない。 |

新規構築、既存業務の整理、途中再開、判断変更、誤ったSSoT／テスト／Doneの訂正、部分反映、読取依頼を試験する。本文を訂正して状態撤回がまだ反映されていない等の途中で別担当が再開する場合も、矛盾を前提に実装せず残りの訂正から復帰できることを確かめる。Hook不発・取得失敗・圧縮・再開でも未確認を合格へ丸めない。条件変更時は影響する評価を更新する。

Issue数、文書量、監査回数、自己報告は完成条件ではない。未確認・部分反映・残作業を現行Projectへ明示し、実装済み・検証済み・導入済み・業務で有効を分けて報告する。
