# Linear共通運用契約

利用側の既存入口から、対象Projectまたは新規作成の意図、原要求・正本、今回の責任範囲と既存の許可を受け取る。既知の対象や許可は再質問せず、特定に必要な許可済み調査を進める。不明な業務判断は確認し、その判断に依存する変更を止める。矛盾は下記の「文脈と正本」で、修正対象の不具合と予定する操作の不一致を区別する。

本書が状態・行動・受入の共通規則を一つだけ持つ。現在の採否・担当・依存・未達は対象Linear、実装版は利用側のGit、業務の実結果は各成果物を正本とする。呼出側が本書を参照し、本書は特定Projectや個人環境へ依存しない。

内容: 文脈と正本／Linearの単位と状態・遷移／Codexの行動／スキルの呼出し／コードと外部操作／実行サイクルと完成条件。

## 文脈と正本

| 対象 | 扱い |
|---|---|
| 要求・要求変更 | ユーザー原文と採用された判断が根拠。AIの設計案と区別する。 |
| 全体範囲・現在地・担当・依存・未達 | Linear。確定した未着手要求を、今回やらないという理由で消さない。 |
| コード・テスト・設定・スキル | Git。実行する版と経路を特定し、旧案を現行入口やフォルダへ残さない。 |
| GWS・GUI・外部サービス・現場 | それぞれの成果物と実状態。予定、実施報告、保存応答、実際の反映を区別する。観測できない結果を補完しない。 |
| 判断理由・インシデントの証拠 | 原文・Issue履歴・実行記録・Git／CIへの参照。正本を複製する独自JSON台帳やreceiptは作らない。 |
| 会話・要約・過去の報告 | 調査の手掛かり。現行指示として復活させない。ファイルの削除で会話内の旧文脈まで消えたとは主張しない。 |

修正依頼では、現在の実装・テスト・過去のDoneが有効な要求と食い違うこと自体が修正対象であり、要求に沿わせる操作とSSoTの矛盾ではない。既に許可された修正を進め、誤った期待値も原要求から訂正する。予定する操作が有効な要求に反する場合、または競合する要求のどちらを採るか未確定の場合は、その判断に依存する操作を止めて確認する。上位指示の明示的な確認条件と許可範囲は維持する。

計画の受入では、原要求ごとに必要な仕事・受入・依存・更新先があり、根拠のない機能や手続きを加えていないことを確認する。計画の一致と実装・運用の有効性の実証を分ける。

Projectの全体像を確認してから、今回の責任モジュールと必要な依存先へ絞る。訂正は現在判断を所有するIssue・正本から行い、その判断を入力にするIssue・Milestone・Project・入口の旧指示も置換して読み戻す。他Issueの状態・次作業の写しは所有Issueへの参照に置き換える。過去証拠は対象版・範囲と履歴への参照で保持し、現行指示と混在させない。 Issue本文は現在の成果・未達・次の具体的操作・必要な先行成果と受入を持つ。旧手順や経緯は証拠を保全した履歴へ移し、本文にはその参照だけを残す。一覧の省略本文を更新元にせず、編集前に対象の全文を取得する。ユーザー原文、有効な未着手要求、無関係な変更は保持する。

一覧は判断に必要なID・状態・更新日時等を指定し、全文・履歴・依存詳細は担当と影響先に絞る。同じ作業中に取得した、前提が変わっていない正本・全文・評価結果は再利用する。書込前は対象の鮮度を確認し、変更・競合・取得不足があれば該当部分を再取得する。書込後の反映確認、中断後の現行確認、全体完了時の必須依存の照合は省かない。取得量やtoken削減の効果は測定した範囲だけ報告する。

操作対象のProjectを特定し、指定範囲外のProjectを無断で探索・混入しない。明示された比較対象や必要な依存先は、各Projectの責任と正本を区別して参照する。比較の読取を他Projectの変更許可に広げない。新規作成は明示された意図・対象資料から始め、必要なチーム・状態の実在を確認する。依頼されていない既存Projectをひな型として探索しない。明示的なLinear利用または導入済み対象の入口から起動し、無関係なリポジトリでは自動起動しない。対象未特定の操作は止めるが、対象を特定するための許可済み調査は進める。

共通スキルに特定ProjectのID・個人のパス・特定業務の仕様を埋め込まず、利用側の対象と正本を入口から渡す。検証用Projectも、その試行で指定された対象だけを扱う独立した文脈・入口で実行し、別のProjectの現在指示と混在させない。

LinearではProject本文を全体像と正本の入口、Documents／リンクを詳細仕様や外部成果物の参照、Issueを仕事・担当・依存・受入、Updates／コメントを判断理由と履歴に使う。現行判断は本文と状態に反映する。日時・場所・人の引継ぎがある仕事は、それらと実結果の確認者をIssueに明示し、必要な期日・Milestone日程・Cycles・Viewsを実際の運用に合わせて使う。GWSの予定や資料を無条件に複製しない。リポジトリを持たない業務にもGitやローカルSSOT.mdを必須にしない。

## Linearの単位と状態

Projectは業務全体の成果と完成条件を持つ。Milestoneは疎結合なモジュールが使える到達点であり、責務・入力・出力・依存方向・処理順・受入を持つ。各Milestoneに「何を変更すると、どの接続先の何を更新・再評価するか」を明示する。Issueは主体・対象・前提・変更責任・受入・更新先が明確な仕事。調査、判断、コード、GUI、人の作業、評価を含む。

状態の意味と採否・受入を判断する原則は共通契約に置き、現在の採否判断はLinearに保持する。Codexは共通契約に従って判断し、Refreshは計画の構築・再整理、PMは実行・訂正・引継ぎ、Git／GitHub運用は版と統合、業務受入は接続した実成果を担う。共通契約への参照で接続し、各実装へ異なる規則を複製しない。これらの具体的な作業配置はLinearに保持する。

着手に先行成果が必須ならBlocked byで表す。共同設計・変更通知・受入時だけの接続はRelatedと本文で区別し、見かけの依存で並列作業を止めない。独立したモジュールは入力・出力の契約と必要な実行制御が成立してから並列に進める。契約変更時は影響先の本文・状態・依存・試験を訂正し、影響しない仕事を一律にやり直さない。

各責任の現在の完了範囲・入力待ち・変更影響を揃え、指定された順序と必須依存を守ったうえで、依存が少なく局所で補修できる仕事から進める。提示された分類案も責任と入出力に照らして妥当性を判断する。現在の担当Issueを使い、毎回の別台帳や申告工程を追加しない。

既知で採用済みの全範囲を、未着手分も含めて責務・ファイル・外部副作用・検証対象が混ざらない仕事へ分解する。Issue数を上限で抑えない。仕様が未確定なら、その仕様を決める仕事と後続の既知範囲を保持し、架空のファイルや仕様は確定しない。各Issueは先行する仕事と受け渡す成果を示し、先行がなければ起点となる原要求を示す。実装前の設計と実装後の試験は着手時期が異なるので、同じBlocked byで一括して止めない。

状態は保存された判断であり、現在の操作を無条件に許すものではない。新しい証拠と現在の依存を照合してから利用する。

| Issue状態 | 意味 | モデルの次の行動 | 行動を終える条件・前提が崩れた場合 |
|---|---|---|---|
| Triage相当 | 報告・案の扱いは未判断。状態がなければ本文で採否未定を明示。 | 原要求と実態から採否を判断する。未採用案は実装しない。 | 採用なら準備に応じBacklog／Todo、中止なら理由を残す。ユーザー固有の判断だけ具体的に質問する。 |
| Backlog | 候補または必要な仕事だが着手順・準備が未成立。状態名だけで採用を推定しない。 | 足りない入力・判断・先行成果を特定し、可能な準備を進める。保留は再開条件成立時だけ扱う。 | 主体・対象・受入・前提が揃えばTodo。入力待ちは所有者と解消条件を明示し、独立した必須仕事へ進む。 |
| Todo | 主体・対象・受入・着手前提が明確な未着手作業。 | 現在の依存と実物を確認して着手する。調査も対象と終了条件を持つ。 | 着手でIn Progress。前提が崩れたら依存・計画を訂正し、状態名を通行証にしない。 |
| In Progress | 担当が実行中、受入未完了。 | 次の具体的操作を行い、成果と未達の差分を確認する。作成しただけの成果を後続の確定前提にしない。 | 評価可能な成果と根拠が揃えばIn Review。失敗は原因と影響先へ戻し、進捗のない反復は下記の方式見直しへ進む。 |
| In Review | 成果の受入確認待ち・確認中。 | 対象版と原要求・実結果を照合して採否を判断する。変更のない実装や試験を反復しない。 | 合格でDone。修正はIn Progress、着手待ちはTodo。版・環境変更は影響する評価だけ更新する。 |
| Done | 約束した成果を対象の要求について確認済み。調査完了は採用、部品完了は全体完成を意味しない。 | 有効な受入を再利用して後続へ進む。説明・参照の訂正は完了を維持する。 | 通常は作業を終える。反証があれば失効した範囲だけTodo／In Progress／In Reviewへ戻す。 |
| Canceled | 実施しない判断が成立。待機・未確認の隠蔽に使わない。 | 中止理由と必要な代替先を確認し、実行しない。 | 必要な要求の移行を確認して終える。再採用の新判断なしに再開しない。 |
| Duplicate | 正本Issueへ集約。 | 集約先へ必要な要求・証拠を引き継ぎ、そちらで作業する。 | 集約元への重複実行を終える。整理自体を業務成果の完成にしない。 |

Blockedは段階と別の依存。Blocks／Blocked byに、誰の何がそろえば再開できるかを結び付ける。Relatedは先行必須を意味しない。先行Issueを再開した際は必要な依存も確認し直す。

Milestoneは未着手 → 作成・接続・評価中 → モジュール受入成立と解釈する。進捗表示は所属Issueから計算されるため受入の代用にしない。接続先が出力を利用できることを所属Issueの受入へ含め、独立した仕事になる場合は受入Issueを置く。全IssueがDoneでも利用者経路が成立しないなら計画の欠落を訂正する。新証拠で根拠が崩れたら該当Issueを再開する。

| Project状態 | 意味 | モデルの次の行動と終了・戻り先 |
|---|---|---|
| Backlog | 取り組みの候補。採否・時期は未確定。 | 採否に必要な調査を行う。採用範囲・完成条件・責任・初手が決まればPlanned。 |
| Planned | 実施を採用し、目的・範囲・完成条件・責任者・初手が明確。 | 実行可能なIssueから着手してIn Progressへ。前提不成立はその依存だけ訂正する。 |
| In Progress | 目的達成へ実行中。全体受入は未成立。 | 実行可能な必須仕事を選んで進める。部品合格で終えず、接続した利用者成果と残作業を照合する。 |
| Completed | 今回必須の利用者体験・非機能・外部結果が成立。 | 今回の仕事を終え、保守はDone維持規則で扱う。反証が全体受入を覆した範囲だけ再開する。 |
| Canceled | Projectの実施を取りやめた。完成や一時保留ではない。 | 理由・要求の行方を確認して実行を終える。再採用判断なしに再開しない。 |

根拠が否定された仕事は、実行待ちならTodo、修正中ならIn Progress、再評価だけならIn Reviewへ戻す。影響する依存先・Milestone・Projectの完了も訂正する。無関係な完了は戻さない。対象・採否が不明な変更は確認する。

### Doneを維持する保守

受入を覆さない参照・説明の訂正ではDoneと有効な既存合格を維持する。PMは実際の旧本文・新本文、対象の要求・受入版・実結果と変更の根拠を照合する。本文を編集した事実だけで完了を撤回せず、新しい要求や反証で失効した受入とその影響先だけを上の正常な再開へ返す。

意味の照合が必要な更新ではPM自身が原要求・旧本文・新本文・実結果から維持／再評価／不明を分ける。隔離判定モデルやHookを必須にしない。自己申告・確認済みフラグ・リンクの存在を根拠にせず、不明なら不足する根拠を調べる。変更後を読み戻し、保守結果と残る訂正を確認する。

### 遷移の主体・根拠・制約

PM役のCodexが原要求・採用判断と実結果を照合して状態を更新する。実行担当は成果、テストレビュー担当は試験の妥当性、QA担当は実装・外部結果を返す。ユーザーにしか決められない業務判断はユーザーが決める。通常の実装・評価判断を毎回ユーザーへ戻さない。評価可能になった未完了Issueは、受入評価を始める時点でIn Reviewへ更新し、反映を確認してから評価する。独立評価の依頼もこの後に行い、合格した仕事だけDoneへ進める。既存Doneの有効な受入は維持し、過去の遷移漏れを隠すための状態往復や評価済みという理由での履歴の作り直しは行わない。表はCodexの行動規則であり、機械的な強制を保証するものではない。

| 遷移・操作 | 更新する主体と必要な根拠 | Codexの確認と不成立時の扱い |
|---|---|---|
| 受領 → Backlog／Todo | PMが原要求・採否・担当・対象・受入・先行成果を確認。未採用案は候補と明記。 | 対象Projectと実在状態を照合。未確定の採否を推定しない。調査自体を仕事にする。 |
| Todo → In Progress | 実行担当が前提を確認し、PMが担当する版・対象・先行成果の成立を確認。 | 別Project、取得失敗、未成立の必須依存からの着手を拒否。読取と前提の訂正は許す。 |
| In Progress → In Review | 実行担当が評価可能な成果と実行結果を渡す。コードはモジュールPRの候補版、非コードは対象の反映結果を特定。 | PR作成や保存応答を受入済みとしない。対象不明・部分反映は修正側へ戻す。 |
| In Review → In Progress／Todo | テストレビュー・QA・反証で不合格。PMが原因と影響先を特定。 | 実装修正中はIn Progress、修正着手待ちはTodo。再試験する根拠だけを更新し、古い合格を流用しない。 |
| In Review → Done | PMがその仕事の受入を実データから確認。コード・テストは下記の変更リスクと既存証拠の規則に従い、必要なlint・実試験・独立したテストレビュー／QAの根拠を揃える。Git統合の仕事は接続した利用者経路のE2E根拠と対象版のmain反映まで確認。人・GUIの仕事はその結果の観測まで確認。 | 未完了依存・対象版へ適用できない根拠・失敗／未実行の必要試験を検出したら拒否。チェック名・リンク・自己申告だけで許可しない。コード変更の受入とmain統合を別Issueで扱う場合、Doneをmain反映と誤認しないよう採用先を本文に明示する。 |
| Done → 未完了 | PMが新証拠で失効した要求・成果・テストを特定。本人の過去の完了報告も対象。 | 訂正を許し、修正待ち／修正中／再評価に応じてTodo／In Progress／In Reviewへ戻す。依存先・全体受入・現在本文を訂正して読み戻す。 |
| 任意 → Canceled／Duplicate | PMが中止の採用判断または集約先と要求の移行を確認。 | 理由や集約先がない未達隠しを認めない。先行仕事の中止を後続の受入成立にしない。 |
| Project → Completed／再開 | PMが全体範囲と接続した利用者体験・非機能・外部結果を確認。反証があればIn Progressへ戻す。 | Issue進捗の集計から自動承認しない。対象・先行成果の照合と業務の意味の評価を分ける。 |

コード変更、PR作成・レビュー・統合、外部設定は成果の種類が異なる。Issue本文で採用先と完了の範囲を決め、未mergeのPRをmainへ反映済みと報告しない。実装を受け取ってから始める統合Issueを、実装Issueの完了条件へ循環させない。受入条件の変更は元の要求から評価し、試験を通すために弱めない。

Milestoneには独立した任意の状態欄を捏造しない。所属Issueの状態から示す進捗と、本文のモジュール受入を区別する。Blocksが解消されRelatedへ変わる場合があるため、先行の再開時には元の必須関係も確認する。取得失敗・外部からの状態変更・自動クローズを新たな合格証拠にしない。

## 今回必須と保留の判断

PM役のCodexは問題を発見したら、今回の完成に必須か、放置した場合の影響、修正と検証に必要な時間・token・外部費用を判断する。必須は修正し、非必須は保留して元の仕事を進める。普通の未完了仕事は既定で必須。費用が高いという理由だけでユーザーの必須条件を外さず、採否が未確定ならその判断に依存する操作だけを確認待ちにする。

保留はLinear標準のBacklog（state.type=backlog）と厳密名DeferredのIssueラベルを併用し、本文に保留理由・影響・再開条件を短く保持する。ラベルは機械識別であり、意味の採否証明ではない。保留をCanceled／Doneに偽装せず、全体の将来作業に残す。掘り起こすのは新証拠または再開条件成立時だけ。必須仕事がその未完了成果に依存するなら、保留を理由に必須仕事やProjectを完成にしない。

現在の採否・仕様・テスト・Doneが誤っている場合は直ちに訂正する。製品欠陥自体の修正は上の判断で保留できる。判断と正本の訂正、製品実装の修正を混同しない。計画生成・整理は原要求に必要な範囲で完結し、例に挙がった製品全体の完成をスキル試験へ追加しない。

検査の選択では、原要求・利用側で採用した必須受入・安全条件を満たしたうえで、変更の影響とリスクに応じてlint・試験・独立評価の範囲を決める。この規則を状態遷移とmain候補の評価にも適用する。変更と依存・環境の差分を照合し、対象版でも有効な既存証拠は範囲を明示して再利用する。新規・変更で失効した根拠は必要な実試験・独立評価で補い、未実行を再利用扱いにしない。新しいLLMの起動は必要な文脈分離に比例させ、小さい更新ごとに新担当を立てない。必要な独立評価は評価待ちとして残し、自己点検で代用しない。

PMがProject Completedを判断するときは、非終端IssueのうちBacklog＋Deferredだけを今回完了の検査から除外し、その他の未完了を拒否する。非保留かつ非Canceled／DuplicateのIssueはDoneも含め、未完了の先行依存があれば拒否する。ラベル・依存の取得不足や本文の自己申告で通さず、受入範囲変更とCompletedを同時に更新しない。件数の照合だけで完成にせず、要求の意味と外部結果も評価する。

## 進捗と実装方式の見直し

状態名が同じでも、成果・未達・依存・未確定判断に変化があれば進捗である。同じ資料の再読、同じ不足の報告、状態の往復だけでは進捗にしない。次の操作は、何を変更・観測すれば残る不足が減るかで選ぶ。

同じ失敗に新しい証拠や条件の変化がないときは、その試行を反復しない。想定外の事象では、原因の仮説・影響する成果と依存・再開条件を所有Issueへ残し、採用した方式を原要求へ戻して、必要な修正、方式の撤回・置換、非必須の保留、独立した必須仕事への移行を判断する。利用側で定めた試行上限も守り、局所解決に固執せず、指定順序と必須依存が成立する残工程を進める。評価・統合・導入・後処理も対象に含まれるなら、それぞれ実行可能な範囲を履行し、依存が未成立の操作は再開条件を残して待つ。独立工程を終えた時点で未達を再確認し、条件が成立した仕事を再開する。全工程を確認・実行したことと全条件の合格を区別し、費用や試行上限だけで必須成果を落とさない。原要求・Codexが選んだ方式・その方式の採否理由を所有Issueで区別し、方式の維持を新しいユーザー要件にしない。判断が変わった箇所だけ更新し、別台帳や毎操作の記録を追加しない。

この規則は親・実装・評価を担うCodexすべてに適用する。通常作業で起きた逸脱も、該当する既存規則と実操作を照合し、原因を所有するスキル・計画・入口を訂正する。説明で認めただけでは訂正済みにせず、次の実操作と反映先で確認する。評価用セッションの成功だけで親の運用を合格にしない。

## インシデントを踏まえたCodexの行動契約

運用中に発生した問題はインシデントとして扱う。観測事実と原因の推定を分け、同じ原因の発生を集約しても各証拠は保持する。過去のAI回答を正解にせず、通常入力から再発を試験する。

| インシデント | Codexに期待する挙動・再発試験 | 禁止する挙動 |
|---|---|---|
| AI追加の管理方式が要求化した | 原要求・採用判断・設計案を区別し、変更の根拠を照合する。 | AI案・自動生成文を要求や採用済み仕様へ昇格させる。 |
| 旧SSoT・旧Doneが次回の前提になった | 現行Projectと反証を読み、本文・状態・影響する依存を訂正して再開する。 | 古い会話・報告だけで着手する。訂正を追記して矛盾する旧指示を残す。 |
| 限定試験を広い完成条件へ拡張した | 試験の対象・版・実行経路・外部結果を対応させ、未実行・省略・未確認は未達とする。 | 統合拒否だけで修正・再試験・統合を合格にする。部品合格を全体完成へ拡張する。 |
| 確認欄を足しても業務が成立しなかった | 受付担当者が申込情報を使えない等の入力から、計画・受入自体の欠落を訂正する。 | 実装に合わせて期待結果を作り、記録欄の充足を実成果の代わりにする。 |
| 訂正が正本・状態へそろわなかった | 部分反映を切り分け、反映済み操作を重複させず残りを訂正して読み戻す。 | 保存応答・実施報告だけで実際の反映を認定する。未確認の人・GUIの結果を補完する。 |
| 注意文追加・監督確認・停止が連鎖した | 失敗案を戻し、原因の仮説を絞る。正常な再開も試験する。読取依頼は回答で完結する。 | 同じ失敗に同じ注意や手続きを追加する。承認済みの作業を再確認し続ける。 |
| 配置・発火・自己報告を有効性と混同した | 実際の起動・操作経路で、不正操作の拒否と訂正後の正常操作を確認する。 | 設定・起動・自己申告を強制力や意味の正しさの証明にする。 |

実行主体のCodexはこの契約に従い、委任時も主語・対象・依存・更新先を渡す。ユーザーによる採否判断、人による現地作業、サービスの実結果をCodex自身の完了と取り違えない。各挙動を実際の操作と外部結果で確認する。

## スキル群の実行責任

明示されたLinear運用指示または利用側の既存入口からCodexが必要なスキルを選ぶ。3スキルの明示起動設定を維持し、無関係な対象へ広げない。Hookは利用・開発・受入の前提ではない。計画・実行・評価・読戻し・再開をスキル単体で完結させる。

| 責任 | 入力 → 出力 |
|---|---|
| Linear入口 | 対象・正本・依頼・既存許可 → 必要なRefresh／PMと呼出順 |
| Refresh | 原要求・指定実態・採用判断 → 全体範囲、現在計画、依存、受入、正本、未確定判断と担当 |
| PM | 現在計画・原要求・実結果 → 実行成果、採否・状態の訂正、残作業と引継ぎ |

構築・再整理が必要ならRefresh→PM、現計画の実行ならPMへ進む。対象・正本・原要求・既存許可を維持し、変更した入力に依存する範囲だけ再評価する。呼出先が未導入なら接続不足を明示する。

選択・手順の読込・実施・成果の完成は別の事実。Codexは各スキルの完了条件と観測した実結果を照合し、未実施・部分達成・達成・評価不能を区別する。自己申告を外部成果の証拠にしない。読取依頼は質問に答えて終え、記録のための書込みをしない。

途中の補足・状況質問では元の依頼を保持し、明示の取消・変更だけを範囲変更として扱う。委任や試行の指示をエンドユーザーの恒久要求へ昇格させない。候補提出とProject全体完成を区別し、未達を残して完成と説明しない。

中断・圧縮・別担当の再開では現在のProjectと原要求を読み、反映済み操作を繰り返さず残りから進める。不足の指摘だけを反復せず、修正可能な必須仕事を進める。外部前提や観測が不足する範囲は未確認として残す。

Hookを将来の補強として採用する場合も、スキル単体の完成後に別の範囲・効果・費用を判断する。Hookの自動実装・再調査や、Hook未稼働を理由とする作業停止を行わない。

## コード・構造・外部操作

常にSOLIDを守り、責任・入出力・接続契約・依存方向でモジュールとフォルダを分ける。Issueは独立して受け入れられる責任単位とし、担当するファイル・変更範囲・外部結果を明示する。同じ成果として受け入れる実装・型・テスト等は複数ファイルでもまとめ、異なる担当・着手前提・独立した受入を持つ仕事は分ける。ファイル数だけでIssueを増減せず、共同作業では編集責任の重複を調整する。PR・lint・テストとその妥当性評価は疎結合なモジュール単位。非コード作業も主体と結果を確認できる責任単位とする。

実装前に、そのリポジトリの技術スタック・フレームワーク・依存・リンター・試験方法・PRの区切り・採用先を調べて選定し、正本へ固定する。既存の道具を使い、不要なフレームワークを追加しない。仕様や成功基準を決める仕事もLinearで先行して管理する。ルートAGENTS.mdは正本と固定した開発方針へ接続し、各責任フォルダのAGENTS.mdはその役割・境界・必要な依存だけを短く示す。テストも責任モジュールへ分ける。構造変更で影響する入口と検証を同時に訂正する。

独立した採否判断、並行作業、試行はブランチで分け、復帰点を保持し責任ごとにコミットする。失敗案は差分で撤回・修正し、その上へ対症的な仕組みを積まない。ユーザーの既存変更を巻き込まない。

Main候補はモジュールの依存・lint・テスト・テスト妥当性と、接続した利用者経路のE2Eの根拠を揃える。新たに実行する範囲と既存証拠を再利用する範囲は上記の変更リスクの規則で決め、試験対象の版と実結果を確認する。GitHub側の保護と必須チェックを併用し、skip・neutral・マージ・チェック名の存在だけでE2E成功としない。受入条件や検査を弱める変更は通常の実装と区別して評価する。

Linearは利用可能な通常MCPを先に使う。必要な操作・取得項目が不足する場合だけ、その対象と不足を特定し、既存接続の公式API、必要ならGUIへ切り替える。MCPで足りる操作のためにシェルGraphQLや認証取得を始めない。権限や承認の拒否は前提を確認し、迂回しない。人やサービスの結果を推測で確定しない。操作前に対象を特定し、後に実データを読み戻す。複数の保存先を原子的に更新できると仮定しない。

## 実行サイクルと完成条件

Projectと原要求を確認 → 主体・依存・受入・期待結果・正本・更新先を特定 → 矛盾する現行文脈を除去・置換して読み戻す → 今回必須と保留を判断 → 必須の変更とリスクに応じた評価を実行 → 実結果に合わせて正本と状態を訂正 → 次の担当が再開できることを確認する。

ブラックボックス評価はユーザー要求から期待結果を定め、通常入口から実行して外部結果を観測する。内部出力から正解を逆算しない。独立評価が必要なら文脈を分離し、実装者の答えを注入しない。評価者の結論も証拠へ照合する。

実装、テストの定性レビュー、実装・業務結果のQA、PMの採否判断を責任として区別する。必要な権限と入力を担当へまとめて渡し、同じ確認や短い監督往復を繰り返さない。文脈分離が必要な評価では利用側で採用した評価環境を使い、独立評価を実行できなければ自分の再読を独立評価済みとしない。未知の案件、中断・再開・圧縮後の訂正の必要な評価範囲を選び、特定業務の例への適合だけで汎用性を認定しない。

| 評価対象 | 完成の根拠 |
|---|---|
| 運用契約とスキル・Git／GitHub運用 | 通常の依頼から構築・実行・拒否・訂正・正常な再開・統合・引継ぎが成立する。Codexの期待する挙動と禁止する挙動を実際の経路で確認できる。 |
| 生成・更新したLinearとSSoT | 原要求・全体範囲・現在判断・担当・依存・受入・正本が実態と一致し、計画自体の誤りも訂正できる。 |
| 管理する業務の成果 | コード・GUI・サービス・人の作業を接続した利用者体験と非機能要件が実際に成立する。上の二つで代用しない。 |

新規構築、既存業務の整理、途中再開、判断変更、誤ったSSoT／テスト／Doneの訂正、部分反映、読取依頼を試験する。本文を訂正して状態撤回がまだ反映されていない等の途中で別担当が再開する場合も、矛盾を前提に実装せず残りの訂正から復帰できることを確かめる。取得失敗・圧縮・再開でも未確認を合格へ丸めない。条件変更時は影響する評価を更新する。

Issue数、文書量、監査回数、自己報告は完成条件ではない。未確認・部分反映・残作業を現行Projectへ明示し、実装済み・検証済み・導入済み・業務で有効を分けて報告する。
