# Linear Refresh

[共通運用契約](../linear/references/contract.md)を読み、[Linear入口](../linear/SKILL.md)または明示指示から対象・正本・原要求・今回の範囲・既存の許可を引き継ぐ。状態・採否・訂正の規則は共通契約を使う。本スキルの成果は、実行担当が使える現在の計画である。計画整理の受入に例示製品自体の完成を追加しない。

## 構築・再整理

1. 新規なら提示された意図と資料を起点にする。既存なら指定Projectの全体像・正本入口を読み、今回の整理に必要なリポジトリ・資料・GWS・外部実態・人の引継ぎへ絞る。別Projectを探してひな型にしない。既知情報は再質問せず、不明な業務判断だけを確認する。
2. 原要求・採用判断と実態を対応させ、全体の既知範囲を保持したまま、今回調べる範囲を分ける。共通契約の「今回必須と保留の判断」に従い、将来作業の保持と今回の必須範囲を分離する。未採用案、未確定の仕様・成功基準・技術・権限・観測条件は、決める主体と判断材料を持つ仕事にする。その判断待ちでも既知の後続要求を消さず、架空の仕様やファイルを確定しない。
3. 利用者の外部成果から受入を定め、責務・入力・出力・副作用・更新先が混ざらない仕事へ分解する。コードは対象ファイルとモジュールの検証・PR単位、非コードは実行者・実結果の確認者・日時・場所・共有権限・引継ぎを特定する。後続ごとに必要な受渡しを照合し、その入力だけで進める後続を、無関係な未決事項まで束ねた先行Issue全体のDone待ちにしない。先行責任を独立して受け入れられる判断・成果へ分け、変更時も影響する後続だけを戻す。技術選定はコード実装より先に置く。コードのない業務へGit・lint・ローカルSSOT.mdを足さない。
4. 対象チームの実在するネイティブ状態を確認して共通契約の意味へ対応させる。依頼の採否、Project全体の段階、個々のIssueの準備状態を区別し、一部の準備不足でProject状態の意味を再定義しない。Projectには完成条件と全体の入口を置く。Milestoneは責務・入出力・変更影響がまとまる疎結合モジュールの利用可能な到達点とし、同じ責任の仕様・判断、実装や準備、局所受入を可能な限り一緒に配置する。工程名だけでモジュールとせず、実際のモジュール間の受渡しを明示する。局所受入とは独立に利用者体験全体の受入を確認する。Issueには担当・先行成果・受入・更新先を配置する。必須先行成果はBlocked by、共同設計・変更通知はRelatedに分ける。Docs／リンクは既存正本へ接続し、日程・Cycles・Viewsは実際の運用に必要なものだけ使う。既存項目を照合してから作成・更新し、重複を増やさない。
5. 原要求→仕事→受入と、各仕事→その根拠を双方向に辿る。全IssueがDoneでも利用者が成果を使えないなら、欠けた仕事・責任・受入を計画へ戻す。変更する判断の所有Issueと、それを入力にするIssue・Milestone・Project・入口を特定する。共通契約の「文脈と正本」に従い、所有箇所から影響先の旧指示・状態の写しまで置換し、本文・状態・依存を読み戻す。保存途中なら実際の反映を確かめ、残りの訂正から再開する。

## 実行へ渡す

出力は対象Linearの現在本文・状態・依存と正本参照。新規構築・再整理の結果に合わせ、利用側の既存入口も実在する現行Project、導入済みlinearの実際のSKILL.md参照と開始・再開時の呼出しへ更新して読み戻す。原要求・正本と、ユーザー／呼出元が既に採用した操作範囲・訂正時の確認方針を保持し、許可や方針を創作せず、上位の明示的なユーザー確認要求を尊重する。未導入なら接続不足を残す。全体に残る要求、今回整理した範囲、未確定判断と担当、次に着手できる仕事・必要な先行成果を区別する。変更した入力・受入・依存が影響するPM・Git運用・評価へ訂正を返す。

整理のみの依頼は結果と未確定事項を回答して終える。実行も依頼されている場合は、対象・原要求・正本・既存許可と更新した計画を[linear-pm](../linear-pm/SKILL.md)へ渡す。PMからの再整理依頼では、原因となった反証と訂正結果を返し、元の仕事から再開できるようにする。

完了は、原要求と実態に対応する計画・受入・正本が現在の本文・状態・依存へそろい、後続が未確定事項と実行可能な仕事を区別して使えること。保存応答だけで部分反映を完了にせず、必要な読戻しと依頼範囲への回答・受渡しで確認する。
