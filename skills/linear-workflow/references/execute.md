# 実行して確かめる

今の計画から仕事を進めるとき、直すとき、中断から再開するときに読む。計画そのものが足りないときは[計画をつくる・立て直す](plan.md)へ戻る。

## 着手する

着手したIssueを、チームの「着手中」にあたるステータス（通常はIn Progress）にする。読み戻して反映を確かめる。

依存が成立していない操作だけを待つ。待っている間は、着手できる独立した仕事を進める。

## 状態ごとに何をするか

チームのステータス設定をそのまま使う。意味を読み替えない。

| 状態 | そこで何をするか | 次にどこへ |
|---|---|---|
| Triage相当 | 採否を判断する。採用していない案は実装しない | 採用ならBacklogかTodo。中止なら理由を残してCanceled |
| Backlog | 足りない入力・判断・先行成果を特定する。できる準備は進める | 担当・対象・完了条件・前提が揃えばTodo |
| Todo | 依存と実物を確認して着手する。調査も対象と終了条件を持つ | 着手でIn Progress。前提が崩れたら依存と計画を直す |
| In Progress | 次の具体的な操作を行い、成果と不足の差を確かめる | 評価できる成果が揃えばIn Review。失敗は原因と影響先へ戻す |
| In Review | 完了条件と実際の結果を照合する。対象の版を特定する | 合格でDone。直すならIn Progress。着手待ちならTodo |
| Done | 有効な受入を再利用して次へ進む。説明や参照の訂正では維持する | 反証が出たら、失効した範囲だけ戻す |
| Canceled | 中止の理由と、要求がどこへ移ったかを残す | 再採用の判断なしに再開しない |
| Duplicate | 正本のIssueへ要求と証拠を引き継ぐ | 集約先で作業する |

待ちを隠すためにCanceledやDoneを使わない。保留するなら、Backlogに置いて理由・影響・再開条件を本文に短く書く。保留を理由に、それに依存する必須の仕事を完了にしない。

## コードの仕事

- Linearが提案するブランチ名（Issueの「Copy git branch name」）で作業する
- コミットメッセージにIssue IDを入れる（`MAT-123: 予約一覧のAPIを追加`）
- PRのタイトルか本文にIssue IDを入れる。マージで完了させてよいなら`Fixes MAT-123`、マージ後の環境で確かめるまで完了にできないなら`Part of MAT-123`
- 変更に対応するテストを書いて実行する。バグ修正には、そのバグが再発したら失敗するテストを付ける
- mainへ入れるのは、Project本文に固定した統合基準を満たしたものだけ。チェック名があることやマージできたことを、E2Eの成功にしない

## コード以外の仕事

資料、調査、設定、外部サービスの操作、人への連絡。

- 成果物を作り、Issueにリンクかファイルとして付ける
- 外部での結果は実際に確かめる（送れたか、相手が開けるか、設定が反映されたか）。保存できたという応答や自分の予定で済ませない
- 人にしかできない作業や判断は、その人を担当にしてIssueに残す。人の作業を自分の成果にしない

## 試行を残す

意味のある試行ごとに、コメントを一つ残す。

```
試したこと：
結果：成功 / 失敗 / 不明（何が起きたか）
証拠：PR、ログ、スクリーンショット、リンク
次：
```

失敗は消さない。次の担当が同じ失敗をしないための情報になる。

## 進まなくなったとき

状態名が同じでも、成果・不足・依存・未確定の判断が変わっていれば進んでいる。同じ資料の再読、同じ不足の報告、状態の行き来だけでは進んでいない。

**同じ失敗に新しい情報がないなら、同じ試行を繰り返さない。** 二回失敗したら、原因の見立て・影響する成果・再開条件をIssueに残して、次のどれかを選ぶ。

- 方式を変える
- その方式を撤回して別の方式に置き換える
- 今回必須でないなら保留して、元の仕事に戻る
- 独立した別の必須の仕事へ移る

**デグレや過剰実装のループに入ったら、Gitで戻る。** 失敗した案は差分で撤回する。その上に対症的な仕組みを積まない。だから復帰点を残しながらコミットする。

注意文やチェック項目を足すことで、原因を直したことにしない。

## サブエージェントを使う

文脈を分けることに意味があるときだけ使う。

- 実装者の期待値から切り離して結果を確かめたいとき
- テストコード自体が妥当かを定性的にレビューさせたいとき
- 独立した必須の仕事を並行して進められるとき

渡すのは、通常の依頼・対象・実物・許可だけ。正解の計画、修正箇所、次の操作、採点の資料は渡さない。答えを渡して通した試験は、自律した遂行の証拠にならない。

小さな更新ごとに新しい担当を立てない。独立した評価が必要なのに実行できないときは、評価待ちとして残す。自分の読み直しを独立した評価として扱わない。

## 保存と外部操作

保存や外部操作では、応答が返ったことを成功にしない。業務エラーを検査する。失敗したら、それに依存する後続の操作と状態更新を呼ばない。

反映先を読み戻す。部分的に反映された、タイムアウトした、失敗したときは、成功済みの副作用をやり直さず、未反映と不明を分けて、残りの訂正から再開する。複数の保存先が同時に更新されると仮定しない。

拒否された操作は、対象と前提を確認する。迂回しない。

## 完了にする

- Doneにするのは、完了条件の結果を実際に確かめたときだけ。何で確かめたか、何は確かめていないかをコメントに書く
- 完了条件がマージ後の環境（stagingや本番）での動作なら、そこで確かめてからDoneにする
- 変更が既存の機能に影響しうるなら、関係する過去のIssueの完了条件とテストを確かめる。壊していたら直す
- Projectを完了にするのは、Issueがすべて終わり（Done、Canceled、Duplicate、または理由を書いて保留したBacklog）、さらにProject本文の完成条件を実際に確かめたとき。Issueの進捗の集計で判断しない
- 報告では「作った」「確かめた（何で）」「確かめていない」を分ける。範囲を限った確認を、全体の完成として報告しない

## Doneを維持する保守

説明や参照を直しただけなら、Doneのまま読み戻す。本文を編集した事実だけで完了を撤回しない。

新しい証拠で受入が失効したときは、失効した範囲とその影響先だけを戻す。無関係な完了は戻さない。本文だけ直して状態を戻し忘れていたら、その残りから進める。

## 区切る・引き継ぐ

作業を終えるとき、中断するとき、別の担当へ渡すときは、次の状態にしておく。

- Issue本文が現在地を正しく表している
- 最後のコメントに、次の一手と、待っているものがあればその中身がある
- Projectの節目なら、Project updateを書いてある

中断や別担当からの再開では、過去の報告ではなく、いまのLinearの本文・状態と実データから開始地点を決める。反映済みの操作を繰り返さない。
