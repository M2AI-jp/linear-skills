# Linear Workflow

モデルの出力は確率的で、規律には期待できない。出力の質は渡された入力で決まり、その出力が次の入力になる。だから仕事を収束させるものを、注意書きではなく、状態と機構で持つ。

| 要るもの | 担うもの |
|---|---|
| 目標 | 受入。実装より先に書く。main で緑になった受入が確定仕様 |
| 現在地 | main の受入結果とLinearから、毎回導出する。記憶や過去の報告から決めない |
| 逆戻り止め | 門。緑だった受入を赤にする変更は main に入らない。Linearが現実とずれたままでは止まれない |
| 引き直し | セッションの開始時に、導出した現在地が渡る |

この仕掛けがハーネスで、リポジトリごとに違う。このスキルは、ハーネスを**建てる**ときと、現実とずれたものを**引き直す**ときに使う。日々の進行は、入口と `harness` が運ぶ。

`harness` は、このファイルと同じディレクトリにある実行ファイル。モデルを呼ばず、Linearには書かない。中を読む必要はない。

## ハーネスの型

**入口。** リポジトリ直下の `AGENTS.md`（または `CLAUDE.md`）の1ブロック。人とエージェントと `harness` が同じ行を読む。

```
## 進め方
- 正本: <Linear Project のURL>
- Linearの叩き方: `<GraphQLのJSONを標準入力で受けて、応答のJSONを返すコマンド>`
- 受入: `<コマンド1つ>`（出力は Issue ID ごとの緑・赤）
- モジュール: <ディレクトリ> = <Milestone>、…、. = つなぎ
- 確認が要る: <このプロジェクトで取り消しにくい操作>
```

**受入。** `accept/<Issue ID>_<短い名前>` という実行ファイル。終了コード0が緑。`harness accept` が1本ずつ走らせて `緑 MAT-12 説明` / `赤 MAT-12 説明` を出すので、入口の「受入」にはそれを書く。別のテスト基盤を使うなら、同じ形の行を出すコマンドを書く。

- 1行目のコメントに、観測できる結果を実数で書く。「今日の予約4件が一覧に出る」は結果。「APIを実装する」は作業
- 利用者が通る経路で確かめる。部品が動くことではなく、つないだ体験が成立すること
- 追跡されているファイルだけで走る（CIと同じ場所で走らされる）
- 受入も次のセッションが読む入力。何を守っているかが読めるように書く

**Issue。** 本文に受入を1行で持つ。型は3つ。

```
受入（自動）: 今日の予約4件が一覧に出る accept/MAT-12_list@3f2a1c9
受入（証拠）: 見積を送り、受領の返信がある <完了時に、リンクと日付>
受入（人）: 経理の山田さんが6月分の集計を確かめる
```

自動の所在は `パス@commit`。`harness` は、その版と main の受入を比べる。コードで確かめられない仕事（調査、資料、設定、外部サービスの操作、人への連絡）は、証拠か人にする。本文は最新の事実に上書きし、経緯はコメントに置く。

**状態。** 現実から計算できる述語として使う。食い違えば `harness` が名指しする。

| 状態 | 成り立っていること |
|---|---|
| Backlog | 受入がまだ書けない。粗いまま |
| Todo | 受入があり、main で赤。Blocked by が無ければ前線 |
| In Progress | Issue ID を名前に持つブランチか、メッセージに持つ commit がある |
| Done | 受入が main で緑。証拠なら、リンクがある |
| Canceled | 理由と、要求の移動先がコメントにある。受入は消してある |
| Project 完了 | 開いているIssueが無く、受入が全部緑 |

Blocked by は、先に終わらないと着手できない依存だけに張る。前線のIssueは1本ずつサブエージェントに渡せる。渡すのはIssueと入口だけ。

## 建てる

0からでも、すでにある実態からでもよい。

1. **完成を、観測できる結果で書く。** Project本文に「誰が何をできれば完成か」。それを通しで確かめるIssueを1本、「つなぎ」の Milestone に置く
2. **疎結合なモジュールに割る。** Milestone 1つがディレクトリ 1つ。そのディレクトリとその受入の中で仕事が完結するように切る。工程名で切らない。またぐ仕事は「つなぎ」（ディレクトリは `.`）
3. **Issueに落とす。** 1本は、それだけで完了を確かめられる単位。受入を書いて main に入れ、赤を確かめる。着手前から緑の受入は、何も確かめていない。すぐやらないものは、受入なしで Backlog。分からないことは、調べるIssueにする
4. **受入を別の文脈に攻めさせる。** サブエージェントに、受入とIssueだけを渡して、「受入は通るのに、利用者は使えない」抜け道を挙げさせる。実装はさせない。抜け道があれば受入を直す。実装をまだ始めない場合も、ここでやる
5. **入口を書き、`harness setup` を走らせ、main に commit する。** フックとCIが登録される。各Issueの受入に、その commit を所在として書く

すでに動いているもののうち、壊されたくないものは、受入を書いて緑を確かめ、完了したIssueとして置く。それが確定仕様になる。全部は写さない。

終わりの条件は、`harness check --wellformed` が「整っている」と出すこと。見られるのは、入口の5行、受入コマンドが走ること、開いているIssueの受入と所在、モジュール表とディレクトリ・Milestone の一致、フックの登録、食い違いが無いこと。出なければ、名指しされたものを直す。

## 引き直す

開始時に渡された現在地（`harness status` でも出る）の食い違いを、1件ずつ消す。

- 現実を正とする。Linearの状態を現実に合わせる
- 緑だった受入が落ちているなら、コードを直す。直さないと決めたなら、そのIssueを開き直す
- 古いコード、古い受入、古い記述は消す。残すと次の入力になる
- 意図が変わったなら、建てるの3から5を、変わった分にやり直す。受入を変えてよいのは、基準を変えると人が決めたときだけ。変えたら所在の commit を書き直し、理由をコメントに残す
- 受入そのものが誤っていると思ったら（Project本文の基準と合わない期待値など）、実装した文脈では直さない。受入とProject本文だけをサブエージェントに渡して判定させる。誤りなら直し、所在の commit を書き直し、理由をコメントに残す。基準を変える話なら、人に聞く
- 止まるときは、終わった分を書き戻してから止まる。commit し、Linearの状態を合わせ、残りと待っているものをIssueのコメントに書く。1件の待ちを理由に、ほかの仕事まで止めない
- 中止は Canceled にして、理由と要求の移動先をコメントに書き、受入を消す
- 閉じたIssueはアーカイブしてよい。確定の記憶は、受入と commit が持つ

終わりの条件は、食い違いが「なし」になること。

## 人に聞くこと

聞く：何を達成したいか、受入の基準、優先順位、取り消しにくい操作（お金・公開・削除・送信）。聞いた答えは、Project本文と入口の「確認が要る」に置く。

**答えを待って止まらない。** 決まっていない基準は、仮置きで受入を書いて建て終える。仮置きは Project本文に並べ、人が確かめるIssue（受入（人））を1本立てる。答えが違っていたら引き直す。待つのは、取り消しにくい操作だけ。

聞かない：作り方、分け方、順番、道具。決めて進め、理由をコメントに残す。

## 置き場所

このディレクトリを、リポジトリの `.claude/skills/linear-workflow/`（Claude Code）か `.agents/skills/linear-workflow/`（Codex）に置いて commit する。フックとCIが、そこの `harness` を呼ぶ。Codexは、リポジトリのフックを初回に人が信頼する必要がある。

`harness` は、入口の「Linearの叩き方」のコマンドでLinearを読む。コマンドが無ければ環境変数 `LINEAR_API_KEY` を使う。エージェントがLinearに書くのは、同じコマンドでも、Linear MCP（`https://mcp.linear.app/mcp`）でもよい。どちらも無ければ、人に接続を頼む。
