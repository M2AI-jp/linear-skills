# Linear Workflow

## 解きたい問題

セッションが切れると、前回の結論が失われる。次のセッションは、残っている古いコードと古い完了報告を正しいものとして扱い、同じ場所を壊し直す。全体像を渡しても、Gitで追えない単位の決定は保存されないまま消える。

出力の質は、モデルの性能と、渡された入力で決まる。そして今回の出力は、次のセッションの入力になる。だから入力を汚さないことが最優先になる。Linearは、その入力を置く場所として使う。

このスキルの仕事は一つ。**次に来る担当（別のセッション、別のエージェント、人）が、Linearを読むだけで現在地と経緯をつかんで続けられる状態を保つこと。**

守ることは三つ。

- 現在地はLinearにある。Issue本文はいつも最新の事実に上書きする。経緯は本文に積み上げず、コメントと変更履歴に残す。
- 失敗は消さない。何を試して何が起きたかをコメントに残す。新しい情報がないまま同じ試行を繰り返さない。
- 確かめていないものを完了にしない。

Linearの機能で表せることは、その機能で表す。独自の状態定義、台帳ファイル、進捗JSONを作らない。

## 最初に読む

1. 対象を特定する。手がかりは、ユーザーの指示、Issue IDやURL、ブランチ名に含まれるIssue ID、リポジトリのAGENTS.mdやREADMEにあるLinearのリンク。特定できなければ聞く。指定された範囲外のProjectを探索しない。
2. 対象Issueの本文、直近のコメント（特に最後の試行と失敗）、Relations、親とSub-issue、紐づいたPRを読む。所属Projectの本文と最新のProject updateも読む。
3. 会話の記憶や過去の報告より、いま読んだ内容を優先する。
4. **読むだけ・質問だけの依頼なら、ここで答えて終える。書き込まない。Issueを増やさない。**

## どこに何を置くか

| Linearの機能 | 置くもの |
|---|---|
| Initiative | 複数Projectにまたがる目的。必要なときだけ |
| Project | 一つの成果。本文に「完成とは、誰が何をできる状態か」と、その確かめ方。使う技術・リンター・テスト方法・mainへの統合基準もここかDocumentに固定する |
| Milestone | 疎結合なモジュールが実際に使えるようになる到達点。責務・入力・出力・依存方向・受入を持つ。工程名で切らない |
| Issue | 一つの仕事。本文はいつも「今の正しい状態」：目的、完了条件、分かっていること、次の一手 |
| Sub-issue | 一回の作業で終わらない大きさのときだけ分ける |
| Blocked by | 先に終わらないと着手できない依存だけ。関係があるだけならRelated。重複はDuplicate |
| コメント | 試行の記録。何をして、どうなったか（失敗も含む）、証拠、次の一手 |
| Project update | 節目の状況報告と健康度、その根拠 |
| Document | 長い仕様、調査結果、決定の記録 |
| ステータス・ラベル・優先度 | チームにある設定をそのまま使う。意味を読み替えず、新設は避ける |
| GitHub | コード、テスト、PR、CI、コミット履歴。コードについての事実はこちらが正しい |

## 三つのモード

依頼を読んで、どれかを選ぶ。全部やる必要はない。

| 依頼 | すること |
|---|---|
| 現状を知りたい・説明してほしい | 上の「最初に読む」で答えて終わる |
| 新しく計画する、または計画が実態と合っていない | [計画をつくる・立て直す](references/plan.md) |
| 今の計画から進める、直す、再開する | [実行して確かめる](references/execute.md) |

計画の作り直しから実行まで求められたら、計画を直してから実行へ進む。

## 汚染に気づく

古いコンテキストがリフレッシュされないことが、この仕組みが防ぎたい最大の失敗。汚染は自分では見えないので、合図を決めておく。次のどれかに出会ったら、作業を続ける前に現在地を直す。

- Issue本文やProject本文の記述と、実際のコード・設定・外部サービスの状態が食い違う
- Doneなのに、その完了条件の結果が今は成立していない
- テストが通っているのに、利用者の経路では成立しない
- 同じ不足を二回以上報告している、または状態を行き来させただけで成果が変わっていない
- 本文に、どのIssueが所有しているのか分からない手順や、別Issueの状態の写しが残っている

直す順番は、その判断を所有しているIssueが先。次に、その判断を入力にしているIssue・Milestone・Project・リポジトリのAGENTS.mdを直す。直したら読み戻して反映を確かめる。

## 聞くこと、聞かないこと

聞く：何を達成したいか、受け入れの基準、優先順位。お金・公開・削除・送信など取り消しにくい操作。

聞かない：作り方、分け方、順番、使う道具。自分で決めて進め、理由をコメントに残す。すでに許可された作業を確認し直さない。依存が成立していない操作だけを待ち、着手できる独立した仕事は進める。

## しないこと

- Linearの外に進捗の台帳や状態ファイルを作る。進捗はLinear、コードの事実はGitHubにある。
- 自分で決めた方式を、ユーザーの要求に昇格させる。
- 管理の仕組みを整える作業に、本来の仕事より多くの時間を使う。
- 確かめていないことを完了・完成として報告する。
- 変化のない確認や、形だけのコメントを繰り返す。記録するのは意味のある変化だけ。
- 規則やチェック項目を増やすことで、実装されていない機能を埋めたことにする。

## 接続

Linearは使える公式の手段（Linear MCP `https://mcp.linear.app/mcp` など）で操作する。つながっていなければユーザーに接続を頼み、それまでは読み書きできないことを伝える。PRとCIは`gh` CLIやGitHub MCPで確かめる。Linearに書き込んだら読み直して反映を確かめる。保存できたという応答だけで済ませない。
