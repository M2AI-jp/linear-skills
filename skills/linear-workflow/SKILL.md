# Linear Workflow

セッションが切れると前回の結論が失われ、次のセッションは古いコードと古い完了報告を正しいものとして扱って同じ場所を壊し直す。出力の質は渡された入力で決まり、その出力が次の入力になる。Linearは、その入力を汚さずに置く場所。

この三つが全部の根拠。以降は、これをどこに書くかの話。

1. **現在地はLinearにある。** Issue本文は最新の事実に上書きする。経緯はコメントと変更履歴へ。
2. **失敗は消さない。** 新しい情報がないまま同じ試行を繰り返さない。
3. **確かめていないものを完了にしない。** 保存できたという応答、チェック名の存在、人の作業、自分の予定は、どれも確かめたことにならない。

Linearの機能で表せることはその機能で表す。独自の状態定義、台帳ファイル、進捗JSONを作らない。管理の整備に本来の仕事より時間を使わない。

## 最初に読む

対象を特定する。手がかりは、ユーザーの指示、Issue IDやURL、ブランチ名のIssue ID、リポジトリのAGENTS.mdやREADMEにあるLinearのリンク。特定できなければ聞く。指定範囲外のProjectを探索しない。

対象Issueの本文、直近のコメント（特に最後の試行と失敗）、Relations、親とSub-issue、紐づいたPR、所属Projectの本文と最新のProject updateを読む。会話の記憶より、いま読んだ内容を優先する。

**読むだけ・質問だけの依頼なら、ここで答えて終える。書き込まない。**

## どこに何を置くか

| 機能 | 置くもの |
|---|---|
| Project | 一つの成果。「完成とは誰が何をできる状態か」と確かめ方。使う技術・リンター・テスト方法・mainへの統合基準 |
| Milestone | 疎結合なモジュールが実際に使える到達点。責務・入出力・依存方向・受入。工程名で切らない |
| Issue | 一つの仕事。目的、完了条件、分かっていること、次の一手。**成果がどこにあるか（ブランチ・commit・PR、資料ならそのリンク）** |
| Blocked by | 先に終わらないと着手できない依存だけ。関係があるだけならRelated、重複はDuplicate |
| コメント | 試したこと／結果（失敗も）／証拠／次 |
| Project update | 節目の報告と健康度、その根拠 |
| Document | 長い仕様、調査結果、決定の記録 |
| ステータス・ラベル | チームの設定をそのまま使う。意味を読み替えず、新設は避ける |
| GitHub | コード、テスト、PR、CI。コードについての事実はこちら |

## 計画をつくる・立て直す

既存のProjectとIssueを検索して重複を作らない。

**実装に入る前に、完成を観測できる結果で書く。** 「受付担当が管理画面で今日の予約一覧を見られる。stagingで別ブラウザから4件見える」は完了条件。「APIを実装する」は作業内容。E2Eで何を確かめるかもここで決める。あとで決めると実装に合わせて期待値が下がる。テストコードも次が読む入力なので、何を守るテストかが読めるように書く。

Issueは**それだけで完了を確かめられる単位**にする。一緒に受け入れるもの（実装と型とテスト）はファイルが複数でも一つにまとめ、担当・前提・受入が別のものは分ける。ファイル数でIssueを増やさない。細かくするのは失敗の範囲を小さくするためで、管理項目を増やすためではない。すぐ着手しないものは粗いままBacklogへ。

**分からないことは調べるIssueにする。** 誰が決めるか、何を材料にするか、何に影響するか。調べて初めて分かることを着手の前提にしない。

できたら両方向に辿る。達成したいこと→仕事→受入→更新先。各Issue→なぜ必要か。**全IssueがDoneでも利用者が成果を使えないなら計画が欠けている。** つないだ体験は部品とは別に成立させる。将来の仕事もBacklogに残す。

リポジトリを持つ仕事なら、直下の `AGENTS.md`（または `CLAUDE.md`）に対象ProjectのURL、毎回読む正本、触ってよい範囲と確認が必要な操作を書く。**これがないと次の担当は対象を特定できない。**

立て直すときは、判断を所有しているIssueを先に直し、次にその判断を入力にしているIssue・Milestone・Project・AGENTS.mdを直す。他のIssueの状態を写していた箇所は参照に置き換える。直したら読み戻す。

## 実行する

着手したIssueをチームの「着手中」にする。依存が成立していない操作だけを待ち、着手できる独立した仕事は進める。

| 状態 | そこで何をするか | 次にどこへ |
|---|---|---|
| Backlog | 足りない入力・判断・先行成果を特定し、できる準備を進める | 担当・対象・完了条件・前提が揃えばTodo |
| Todo | 依存と実物を確認して着手する。調査も対象と終了条件を持つ | 着手でIn Progress。前提が崩れたら計画を直す |
| In Progress | 次の具体的な操作を行い、成果と不足の差を確かめる | 評価できる成果でIn Review。失敗は原因と影響先へ |
| In Review | 完了条件と実際の結果を照合する。対象の版を特定する | 合格でDone。直すならIn Progress、着手待ちはTodo |
| Done | 有効な受入を再利用して次へ進む | 反証が出たら失効した範囲だけ戻す |
| Canceled | 中止の理由と、要求がどこへ移ったかを残す | 再採用の判断なしに再開しない |

待ちを隠すためにCanceledやDoneを使わない。保留するならBacklogに置いて理由・影響・再開条件を書く。保留を理由に、依存する必須の仕事を完了にしない。

コードでは、Linearが提案するブランチ名を使い、コミットとPRにIssue IDを入れる（マージで完了してよいなら `Fixes MAT-123`、マージ後の環境で確かめるなら `Part of MAT-123`）。変更に対応するテストを書き、バグ修正には再発したら失敗するテストを付ける。mainへ入れるのはProject本文の統合基準を満たしたものだけ。

コード以外では、成果物をIssueに付け、外部の結果を実際に確かめる（送れたか、相手が開けるか、設定が反映されたか）。人にしかできない作業はその人を担当にして残す。

保存や外部操作では業務エラーを検査し、失敗したら依存する後続操作と状態更新を呼ばない。反映先を読み戻す。部分的に反映されたら、成功済みの副作用をやり直さず残りから再開する。

文脈を分けることに意味があるときだけサブエージェントを使う。実装者の期待値から切り離して結果を確かめたいとき、テストコードの妥当性を評価させたいとき、独立した仕事を並行するとき。渡すのは通常の依頼・対象・実物・許可だけ。**正解の計画・修正箇所・次の操作を渡して通した試験は、自律の証拠にならない。** 自分の読み直しを独立した評価にしない。

## 詰まったとき

成果・不足・依存・未確定の判断が変われば進んでいる。同じ資料の再読、同じ不足の報告、状態の行き来は進んでいない。

二回失敗したら、原因の見立て・影響する成果・再開条件を残して、方式を変える／別の方式に置き換える／今回必須でなければ保留して元の仕事に戻る／独立した別の必須の仕事へ移る、のどれかを選ぶ。

**デグレや過剰実装のループに入ったらGitで戻る。** 失敗した案は差分で撤回し、その上に対症的な仕組みを積まない。だから復帰点を残しながらコミットする。注意文やチェック項目を足すことで原因を直したことにしない。

## 汚染に気づく

古いコンテキストがリフレッシュされないことが、防ぎたい最大の失敗。自分では見えないので合図を決めておく。次のどれかに出会ったら、作業を続ける前に現在地を直す。

- 本文の記述と、実際のコード・設定・外部サービスの状態が食い違う
- Doneなのに、その完了条件の結果が今は成立していない
- テストは通っているのに、利用者の経路では成立しない
- 同じ不足を二回以上報告している、または状態を行き来させただけで成果が変わっていない
- どのIssueが所有しているか分からない手順や、別Issueの状態の写しが本文に残っている
- 本文が「実装済み」「作成済み」と言っているのに、**その成果物に到達する手段が書かれていない**（ブランチ・commit・PR・リンクのどれもない）。到達できない成果は、事実として扱わずに所在から確かめ直す

## 完了にする

Doneにするのは完了条件の結果を実際に確かめたときだけ。何で確かめたか、何は確かめていないかを書く。完了条件がマージ後の環境での動作なら、そこで確かめてから。変更が既存機能に影響しうるなら、関係する過去のIssueの完了条件とテストを確かめ、壊していたら直す。

説明や参照を直しただけならDoneのまま読み戻す。反証で受入が失効したら、失効した範囲とその影響先だけ戻す。

Projectを完了にするのは、Issueがすべて終わり、さらにProject本文の完成条件を実際に確かめたとき。Issueの進捗の集計で判断しない。

報告では「作った」「確かめた（何で）」「確かめていない」を分ける。範囲を限った確認を全体の完成として報告しない。

区切るとき・別の担当へ渡すときは、Issue本文が現在地を正しく表し、最後のコメントに次の一手と待っているものがある状態にする。再開では、過去の報告ではなく、いまの本文・状態と実データから開始地点を決める。

## 聞くこと、聞かないこと

聞く：何を達成したいか、受け入れの基準、優先順位。お金・公開・削除・送信など取り消しにくい操作。

聞かない：作り方、分け方、順番、使う道具。自分で決めて進め、理由をコメントに残す。すでに許可された作業を確認し直さない。

## しないこと

- Linearの外に進捗の台帳や状態ファイルを作る
- 自分で決めた方式を、ユーザーの要求に昇格させる
- 変化のない確認や、形だけのコメントを繰り返す
- 規則やチェック項目を増やすことで、実装されていない機能を埋めたことにする
- **仕事が終わったあとに、検証のための検証を作る**

## 接続

Linearは公式の手段（Linear MCP `https://mcp.linear.app/mcp` など）で操作する。つながっていなければユーザーに接続を頼む。PRとCIは `gh` CLIやGitHub MCPで確かめる。書き込んだら読み直して反映を確かめる。
