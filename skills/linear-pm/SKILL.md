# Linear PM

[共通運用契約](../linear/references/contract.md)を読み、[Linear入口](../linear/SKILL.md)または明示指示から対象・原要求・正本・今回の責任範囲・既存許可を引き継ぐ。状態と受入の判断は共通契約を使う。読取だけの依頼なら、必要な対象を読んで元の質問へ回答し、Issue更新や実行工程を増やさない。

## 現在の計画から進める

1. 通常MCPで現行Projectの全体範囲と未達を確認し、担当Issueまたは必要なIssue集合、その依存・正本・実行版へ読む範囲を絞る。不足する操作・取得項目だけを共通契約の「コード・構造・外部操作」の代替経路へ渡す。別担当・中断・圧縮からの再開でも、過去報告ではなく現在本文・状態と実データから開始地点を決める。
2. 原要求と現在の仕様・テスト・Doneを照合する。反証があれば、誤った判断と影響先を特定して共通契約の正常な再開・訂正を行う。追加改善や製品欠陥は共通契約の「今回必須と保留の判断」を適用し、採否訂正と実装修正を分けて元の必須仕事を続ける。本文だけ訂正済みで状態撤回が未反映なら、その残りから進める。計画の分解や受入自体が不足する場合は、反証・対象・正本・既存許可を[linear-refresh](../linear-refresh/SKILL.md)へ渡し、返った計画から実行を再開する。
3. 今回の主体・対象・先行成果・副作用・観測先・更新先を揃え、共通契約の状態別の次の行動に従って実行する。成果・未達・依存が変わらない反復は「進捗と実装方式の見直し」へ戻す。ユーザーにしかできない判断や人の現地作業は担当へ残し、既に許可された実装・訂正を再承認待ちにしない。依存する仕事が待機中でも、実行可能な独立した責任は進める。
4. コード変更では、そのリポジトリで採用した技術・責任境界・復帰点に従い実装し、必要なlint・試験を行い、テストの妥当性評価・QAへ渡す成果と対象版を揃える。Gitの実装候補、PR、採用、検証版の統合を別の成果として照合する。非コードでは実際の成果物・共有権限・引継ぎと観測結果を確認し、コード用の工程を形式的に追加しない。
5. 保存や外部操作では、`await`の完了だけを成功とせず、MCPの`isError`・業務エラーを検査する。失敗なら同じバッチ内も含め、依存する後続操作・状態更新を呼ばない。反映先を読み戻し、部分反映・タイムアウト・失敗では成功済みの副作用を再実行せず、未反映と不明を分け、残る本文訂正→反映確認→状態判断の順に再開する。人やサービスの実結果を自己報告で補完しない。拒否された操作は対象・前提を確認し、許可された正常な訂正と再評価を経て再開する。
6. 共通契約の「遷移の主体・根拠・制約」に従って評価開始時の状態を反映し、原要求に対する外部結果と対象版から受入を判断する。誤テストは期待結果を原要求へ戻して訂正し、影響する版・完了・依存を再評価する。独立評価が未実行なら評価待ちを保持する。部品の合格で利用者の成果が成立しない場合は、計画へ反証を返す。

## 訂正と引継ぎ

Doneの保守では共通契約の「Doneを維持する保守」に従い、旧本文・新本文と既存受入を照合する。維持できる本文訂正はDoneのまま読み戻し、反証は失効した受入と影響先だけ再開する。判定が不明・拒否なら不足する本文や根拠を訂正し、反映済み更新や無関係な合格を繰り返さない。

清掃は各変更・反証の時点から行う。共通契約の「文脈と正本」に従い、判断所有箇所を先に訂正し、その判断を使う本文に残る旧指示・他Issueの状態の写しを置換する。影響先の本文・状態・依存を読み戻し、部分反映なら未反映箇所を次の開始地点にする。Issueまたは必要なIssue集合の中で、今回の成果と残作業を確認するまで進める。記録済み結果の再書込や同じ監督確認を繰り返さない。

終了・引継ぎ時は、成果物と実行版、実際に行った評価、未達・部分反映、未確定判断の担当、次に着手する必須仕事と前提、保留と再開条件を現行Linearから辿れるようにする。新証拠や再開条件なしに保留を再調査しない。全体の未着手要求を保持し、依頼範囲の実装済み・評価済み・統合済み・導入済み・業務で有効を区別して回答する。

完了は、今回の責任の成果が元の依頼と実結果に一致し、必要な本文・状態・依存・成果版の訂正と読戻しがそろったこと。読取は根拠に沿った回答、候補提出の委任は評価可能な候補と未確認の引継ぎで評価する。Project完成の依頼に必須残作業があれば、局所成果を全体の完了にしない。途中補足と親の指示の扱い、外部前提不足からの再開は共通契約に従う。
