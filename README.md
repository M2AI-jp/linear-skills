# linear-workflow

リポジトリの仕事を Linear で進めるためのメタハーネス。1文の意図から、そのリポジトリ専用のハーネス（入口・受入・フック・統合の門）を建てる。建てたあとは、入口と機構が進行を運ぶ。

配布物は2つ。

- [skills/linear-workflow/SKILL.md](skills/linear-workflow/SKILL.md): 建てる・引き直すの手順。判断が要るところ
- `skills/linear-workflow/harness`: 導出と門。Python 3 の標準ライブラリだけで動く。モデルを呼ばず、Linearには書かない

設計と経緯は [DESIGN.md](DESIGN.md)。

## 導入

1. `skills/linear-workflow/` を、導入先リポジトリの `.claude/skills/linear-workflow/`（Claude Code）か `.agents/skills/linear-workflow/`（Codex）へフォルダごと置いて commit する
2. そのリポジトリで「Linearで進められるようにして」と頼む。エージェントが Project・Milestone・Issue・受入を作り、`AGENTS.md` に入口を書き、`harness setup` でフックとCIを登録する
3. `harness check --wellformed` が「整っている」と出れば、建て終わり

`harness` がLinearを読む手段は2つ。入口の「Linearの叩き方」に書いたコマンド（GraphQLのJSONを標準入力で受けて、応答のJSONを返すもの）か、環境変数 `LINEAR_API_KEY`。

Codexは、人がそのリポジトリを信頼し、フックを確認するまで、フックを走らせない（初回だけ）。信頼されていないリポジトリのフックは、読まれもしない。

Codexのサンドボックスの中からは、`.codex` に書けない。既定では `.git` にも書けない。だから Codex で建てるときは、`harness setup` と commit を、人がサンドボックスの外で通す（承認する）必要がある。`harness setup` は書けなかったファイルを言い、建て終わりの判定は、スキルを置いた側のフックが登録されるまで通らない。

頼む前に人が `harness setup` を走らせて commit しておくと、フックの登録は済んでいるので、建てるセッションは人を待たずに「整っている」まで進む（commit をサンドボックスに許しているとき）。入口が無い間、フックは何も出さない。

このリポジトリの `AGENTS.md`、`DESIGN.md`、`accept/`、`tests/` は導入先へコピーしない。

外すときは、置いたフォルダ、`AGENTS.md` の `## 進め方`、`.claude/settings.json` と `.codex/hooks.json` にある `harness` の登録、`.github/workflows/accept.yml` を消す。

## 建てたあとに起きること

| いつ | 何が起きるか |
|---|---|
| 建てた直後 | 前線は、受入を見直すIssue。自動の受入を持つIssueは全部それを待つので、次に入るセッションは、実装より先に受入を攻める |
| セッションを開始する | main の受入結果とLinearから導出した現在地が、文脈に入る |
| 止まろうとする | このセッションで生じたLinearと現実の食い違いが残っていれば、名指しされて止まれない。同じ理由で止められるのは2回まで |
| main に入れようとする | 緑だった受入が赤になる・消える変更は、CIが通さない |

現在地は、たとえばこう出る。

```
現在地（導出 main@4ad8908）
受入  緑 12 ／ 赤 1 ／ 未実装 3
前線  MAT-530 予約の一覧（In Progress、ブランチ mat-530-list（main より 3 先））
      MAT-531 予約の取消（Todo）
待ち  MAT-533 月次の集計（MAT-530 待ち）
食い違い
  MAT-512 今日の予約4件が一覧に出る … Done なのに受入が落ちている
  MAT-498 受入が、Issueに書いた版（3f2a1c9）から変わった: accept/MAT-498_fee
確認が要る  本番の設定変更、送信
```

## ほかの開発に干渉しない

- フックはリポジトリ単位で登録する。語では発火しない
- `AGENTS.md` に `## 進め方` が無いリポジトリでは、`harness` は何も出さずに終わる
- このリポジトリの `skills/` は、Claude Code も Codex もスキルを探さない場所。`~/.claude/skills/` と `~/.codex/skills/` には置いていない。このリポジトリ自身は、機構だけを自分に適用している

前の版（3スキル＋182行の共通契約＋Hook）は 2026-09-23 に配布され、2026-10-14 に他の開発への干渉を理由に撤去された。

## 確かめたこと

合否が状態で決まるものだけを書く。

- **機構。** 書き換えた受入、Done なのに赤い受入、到達できない所在、状態の食い違い、作業ツリーでの受入の変更を仕込むと、`harness` が名指しする。停止の門は新しい食い違いで止め、同じ理由の3回目は通す。統合の門は、緑から赤への変更を拒む。入口が無ければ何も出さない。`python3 -m unittest tests/test_harness.py`
- **このリポジトリ自身。** `harness check --wellformed` が「整っている」を返す。これは建て終わりの判定なので、開いているIssueがある間の話（Project が完了すると「前線が無い」と言う）。新しいセッションを起動すると、登録したフック経由で現在地が渡る（Claude Code）
- **0から建てる。** スキルのフォルダだけを置いた空のリポジトリで、1文の意図を渡された別文脈のセッションが、約3分で Project・Milestone・Issue・受入（全部赤、実数つき）・入口・フックを作った。観測者の `harness check --wellformed` が「整っている」を返した。依頼を変えて5回（ここまでは Claude Code）
- **1文で完成まで。** 建てたリポジトリで「Linearに従ってサブエージェントを好きなだけ呼び出して完成させてください」だけを渡した。終わったあと、追跡ファイルだけの場所で走らせた受入は全部緑、食い違いは「なし」、開いているのは人が確かめるIssue 1本だけ。4回
  - 1組目は、1本目が commit もLinearの更新もせずに止まった（停止の門が、commit されていない変更を見ていなかった。直した）。冷たい2本目が同じ1文だけで、残っていた実装を Issue ID つきで commit して閉じた。建てるときに紛れた受入の期待値の誤りは、自分では直さず、基準と受入だけを渡したサブエージェントに判定させてから直した
  - 2組目は、**停止の門がセッションを2回止めた**（「受入が main で緑なのに Todo」）。セッションはそのつどLinearを直し、3回目に食い違いなしで通った
  - 3組目は、いまの形（受入の見直しを、ほかのIssueが待つIssueにする）。セッションは最初に見直しを取り、サブエージェントに受入8本を攻めさせた。**実装より前に、Project本文と食い違う受入2本と、緩い照合1件が直った。** そのあと2モジュールを並列のサブエージェントに実装させた
  - 4組目は、最終版（`899c40a`）。建てたセッションは見直しを開いたまま終えた。次のセッションは最初に見直しを取り、「見本の出力を固定で返すだけで通る」などの抜け道を別データと境界の受入で塞いでから、サブエージェント3本で実装した。受入5本が緑、食い違いなし
- **受入の見直しは、文章では賭けだった。** 建てるの手順に「別の文脈に攻めさせる」と書いていた間、3回のうち実行されたのは1回（1回は省略、1回は自分で見直して済ませた）。Issueにして待たせる形にしてからは、次に入ったセッションが最初にやった。受入を書いたセッションがその見直しを閉じると、停止の門が止める。このリポジトリでも、IssueのIDだけを渡した別のセッションが見直しを取り、抜け道を2つ塞いで閉じた
- **遮断器。** ファイルを commit せずに止まろうとし、直すことも断ったセッションは、2回止められ、同じ理由の3回目で通った。残った変更は次の現在地に出る
- **関係のない依頼では選ばれない。** 入口の無いリポジトリで、`続きやって`、テストの依頼、線形回帰、linear search、READMEの修正の5件とも、スキルは選ばれなかった

**Codex（0.163.0）。** Codex の本体を3通りに動かした。`~/.codex` は書き換えていない。

OpenAI のモデル（Codex にログインした状態。ネットワークを閉じたサンドボックスで、セッションは残さない）:

- **建てる（フックなし）。** 1文の意図から、Project・Issue（受入の見直しと、人が確かめるIssueを含む）・受入（赤）・入口を作った。フックの登録だけはサンドボックスに拒まれ、人に外で `harness setup` を走らせるよう求めて終えた。人がそれを走らせて commit すると、`harness check --wellformed` が「整っている」。依頼を変えて3回
- **1文で完成まで（フックあり）。** 開始時にフックが現在地を渡し、サブエージェントに受入を見直させて受入を直し、実装し、Linear を閉じた。追跡ファイルだけの場所で走らせ直した受入は2本とも緑、食い違いなし、開いているのは人が確かめるIssue 1本だけ。停止のフックは、止める理由が無く、通した
- **建てる（フックあり）。** 人が先に `harness setup` を走らせて commit した場所（入口はまだ無い）で、1文の意図を渡した。開始時のフックは、入口が無いので何も出さなかった。セッションは Project・Issue（受入の見直しと、人が確かめるIssueを含む）・受入（赤）・入口を作って commit し、人の手を借りずに `harness check --wellformed` の「整っている」まで進んだ（約3分）。停止のフックは走り、止める理由が無く、通した。観測者の判定も「整っている」
- **その場所で続けて、1文で完成まで（フックあり）。** 開始時にフックが現在地を渡し、サブエージェントが受入を見直して抜け道を塞ぎ、別のサブエージェントが実装し、Linear を閉じた。追跡ファイルだけの場所で走らせ直した受入は2本とも緑、食い違いなし、開いているのは人が確かめるIssue 1本だけ（約4分）。建てるときの「実装はまだしないで」は、入口にも Project 本文にも残らなかった
- **既存のコードの上に建てる（フックあり）。** 動いているCLI（コマンド3つ、テスト3本、決まりを書いた `AGENTS.md`）のある場所で、「いま動いているものは壊したくない。次に月ごとの集計を足したい」と頼んだ。セッションは既存のコードにも `AGENTS.md` の本文にも触れずに入口を足し、いまの動作を、緑の受入を持つ完了済みのIssue（確定仕様）として置き、足す分を赤の受入にした。`harness check --wellformed` が「整っている」（約3分）
- **そこで、1文で完成まで。** 受入を見直させてから実装した。追跡ファイルだけの場所で受入3本が緑、もとからあるテストも通り、実際に使って集計が出た。開いているのは人が確かめるIssue 1本だけ（約3分）
- **途中で基準を変える。** 「集計の基準を変える。カテゴリ別ではなく、週ごとの合計にして」と言うと、Project 本文を書き換え、受入を先に差し替えて commit し、別の文脈に見直させ、実装を差し替え、Issueの所在と理由を書き直した。古い基準のコードは残らなかった。受入3本が緑、食い違いなし（約4分）
- この回で見つかって直したもの: 受入3本が4行の起動役で、確かめる中身は共有の `accept/checks.py` にあった。見直しがその補助だけを直しても、機構は受入が変わったことを見なかった（比べていたのは、所在のパスだけ）。受入と同じ置き場の補助も、Issueに書いた版と比べるようにした。直した機構をその場所に置くと、所在が古いままだった確定仕様のIssueが名指しされ、次のセッションが補助の履歴と見直しの記録を突き合わせて所在を書き直し、食い違いなしで終えた。このリポジトリ自身の受入も、テストを走らせるだけの起動役だったので、走らせるテストをIssueの所在に並べた
- **1文で完成まで（フックなし）。** フックを渡さない形でも、エージェントが自分で `harness` を走らせて現在地を得て、同じところまで進んだ（受入3本が緑、食い違いなし）
- この回で見つかって直したもの: 建てたセッションが「実装はまだしないで」というその場の指示を、入口に「現在の許可範囲は計画まで」と書いた。次のセッションは「完成させてください」と言われても、入口に従って実装を断り、許可を求めて止まった。入口の「進め方」は5項目だけにし、それ以外の行は名指しするようにした

この試行は、ユーザーの Codex 設定（`config.toml`）を読まずに走らせた（設定には Linear や画面操作のMCPが入っていて、試行に持ち込めない）。その形では Codex はリポジトリのフックを読まないので、`harness setup` が登録したフックを、そのままの形で起動時に渡している。ユーザーの設定を読む形では、短い依頼で SessionStart と Stop のフックが走り終えることだけを確かめた。ユーザーの指示書（`~/.codex/AGENTS.md`）は、設定を読まない形でも読まれている。

台本どおりに答える手元のモデルにつないだもの（テストになっている。`tests/test_codex.py`）:

- セッション開始時にモデルへ渡る入力に、現在地・スキルの一覧（`.agents/skills/` から）・入口が入る
- commit されていないファイルを残して終わろうとすると Stop が止め、片づければ通り、片づけなければ3回目で通る

Claude につないだもの（Codex が送る要求を受けて、道具なしの Claude に次の一手を1つ決めさせる橋を挟む。シェル・サンドボックス・フック・スキルの一覧は Codex 自身のもの）:

- **建てる。** 1文の意図から、Codex のスキル一覧を見て `SKILL.md` を読み、15手で建てた。観測者の `harness check --wellformed` が「整っている」
- **1文で完成まで。** 開始時に Codex のフックから現在地が渡り、受入の見直しを先に取って受入を直し、実装し、Linear を閉じた。追跡ファイルだけの場所で走らせ直した受入は4本とも緑、食い違いなし、開いているのは人が確かめるIssue 1本だけ。Stop のフックは止めずに通した
- この回で見つかって直したもの: `harness setup` が `.codex/hooks.json` を書けずに落ち、Claude Code 側の登録だけで建て終わりの判定が通っていた。仮置きを Project 本文に書いただけで、人が確かめるIssueを立てなかった

Codexのサンドボックスの中（`.git` に書けない）でも、`harness` は動く。`/tmp` と `TMPDIR` まで書けなくする設定でも、フックが残した結果を読んで現在地を出し、作業ツリーには何も作らない。`harness setup` が書いた `.codex/hooks.json` を、Codexは Project のフックとして認識する（`codex app-server` の `hooks/list`）。

停止の門が Codex で実際に止めて通すところは、台本のモデルと Claude につないだ本体で確かめたもの。OpenAI のモデルの回では、止める理由が生じなかった。Claude につないだ試行では、サブエージェントの道具はモデルに渡していない。
